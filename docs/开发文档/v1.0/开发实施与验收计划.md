# CodeRisk 开发实施与验收计划

**文档版本：** V1.0  
**项目阶段：** 实施前规划；当前文档不证明代码已存在或测试已通过。  
**目的：** 把五份核心设计和两份专项设计转化为可执行、可分阶段验收的开发任务，避免一次性生成整套系统后难以排查。

## 一、实施原则

1. **先检查仓库，再修改代码。** 首次实施必须读取真实目录、依赖、现有文件和运行环境；不能按假定的目录结构覆盖已有实现。
2. **每次只交付一个可验证切片。** 每个切片写清目标、允许改动、非目标、测试命令和验收证据。
3. **先确定性业务，再接入模型。** 先打通认证、任务持久化、异步分发、状态回写和报告读取，再接入 LangGraph。
4. **Go 管业务事实，Python 管分析。** Python 不直接写业务数据库；任务状态、尝试次数、报告生效与审计由 Go 管理。
5. **不以启动成功代替验收。** 每阶段需要测试结果、关键日志/接口证据和失败场景验证。
6. **不伪造量化结果。** 性能、准确率、成本和可靠性数字只能来自真实运行记录。
7. **控制技术复杂度。** Kafka + Celery/Redis 按已确认架构保留，但首版只实现真实业务需要的事件与恢复机制；不提前引入 Milvus、复杂多租户或代码执行沙箱。

## 二、实施前必须统一的契约

编码前所有实现者必须使用同一组规则：

- 任务状态：`PENDING`、`QUEUED`、`RUNNING`、`SUCCEEDED`、`PARTIAL_SUCCESS`、`FAILED`。
- 每个任务最多 4 次业务执行。只有 Go 创建首个执行或接受合法手动重试时分配 `attempt_no`。
- Kafka 重投、Celery 恢复、模型内部重试、LangGraph 修正和恢复扫描不分配新的 `attempt_no`。
- 只有终态任务可重新分析；重新分析创建新任务并保留旧任务/报告。普通追问不创建任务，接受时绑定报告。
- Go + PostgreSQL 是业务事实来源；Outbox 与业务事务同库提交；Python 只通过鉴权接口回调 Go。
- Diff 是不可信输入；不执行用户代码或脚本；外部模型使用必须先告知并取得确认。
- Risk/Hardness/证据/报告结构以《Agent 工作流与证据规范》为准；认证、限额、保留和日志规则以《认证权限与安全设计》为准。

## 三、分阶段路线与验收门

### 阶段 0：仓库现状与环境基线

**目标：** 确认实际仓库与设计文档的差距，不改业务代码。

**工作项：**
- 输出目录树、现有文件说明、依赖版本、运行方式、环境变量清单。
- 检查 Git 状态，确认是否存在未提交修改；不得覆盖用户已有工作。
- 检查 Docker、Go、Python、Node、PostgreSQL/Kafka/Redis 的可用版本与本地端口冲突。
- 将本套最终文档作为唯一设计基线，标注旧文档中的过时决策，不直接删除未备份文件。

**验收：** 现状报告、可复现的环境检查结果、差异列表；不修改业务实现。

### 阶段 1：仓库骨架与本地基础设施

**目标：** 建立可重复启动的最小开发环境。

**工作项：**
- 建立 Go API、Python Agent、React 前端的最小骨架与依赖锁定文件。
- Compose 启动 PostgreSQL、Kafka、Redis；按需启动 Go/Python/前端服务。
- 配置健康检查、服务依赖、独立网络、非敏感示例环境变量。
- 提供 `.env.example` 和中文启动说明；真实密钥不得提交仓库。

**验收：** 全新环境按文档可启动；容器健康状态可检查；应用服务能连到各自依赖；未配置必需生产密钥时生产模式拒绝启动。

**非目标：** 不接入模型、不实现完整业务页面、不添加向量数据库。

### 阶段 2：数据库迁移、认证与用户隔离

**目标：** 先把身份和数据边界做对。

**工作项：**
- 按数据库设计实现迁移、外键、唯一约束、必要索引和回滚策略。
- 实现注册、登录、退出、当前用户接口与短期会话 Cookie。
- 实现用户归属检查；任何任务/线程/报告读取路径都必须从认证身份获取用户 ID。
- 实现基础限流、密码哈希、CSRF/Origin 校验、密钥配置检查。

**验收：** 注册登录测试通过；密码不以明文保存；用户 A 不能访问用户 B 的资源；生产配置不会回退到示例密钥；未登录请求被拒绝。

### 阶段 3：任务生命周期、输入规范化与报告持久化

**目标：** 先用确定性占位分析打通业务闭环，不接模型。

**工作项：**
- 实现 Diff 文本/文件输入、大小和内容限制、外部模型确认记录。
- 实现任务、输入、执行尝试、报告、证据、线程/消息、审计与 Outbox 的最小数据模型。
- 实现创建任务、查看任务列表/详情、查看报告和线程历史。
- 实现状态机、终态约束、报告与尝试关联、单任务当前有效报告约束。
- 可先由测试适配器返回固定结构化结果，验证 Go 的状态和回调校验。

**验收：** 有效 Diff 可创建任务并得到可追溯的演示报告；非法输入和超限输入在创建前拒绝；用户隔离有效；任务状态和报告事务一致。

### 阶段 4：Outbox、Kafka、Celery 与恢复闭环

**目标：** 证明异步链路在重复投递和进程中断下不会丢失业务事实或虚增执行次数。

**工作项：**
- Go 在同一事务写业务记录与 Outbox；发布器可安全重复发布。
- Python 消费者在 Celery 可靠接收后提交 Kafka Offset。
- 消费去重、Celery 恢复和回调重试都沿用原 `task_id`、`attempt_no`、`event_id`。
- 实现 Go 恢复扫描：检查待发布、排队、执行中记录；区分正常执行、恢复窗口与确认不可恢复。
- 配置发布/排队期限、执行期限、恢复窗口和有限重试退避；初始值放在服务配置，依据本地故障测试校准。

**验收：** 重复 Outbox 发布、Kafka 重投、Celery 重启、重复回调和并发手动重试测试通过；基础设施恢复不增加 `attempt_no`；不可恢复任务能正确进入 `FAILED`；过期回调不能覆盖报告。

### 阶段 5：确定性 Diff 分析与证据索引

**目标：** 建立 Agent 不能绕过的事实层。

**工作项：**
- 解析标准 Git Diff，提取文件列表、增删行数、hunk、可定位行和解析限制。
- 生成应用层证据 ID 和只读证据索引；验证文件路径与行号。
- 对不支持语言、截断 Diff、重命名、异常编码和无法定位行号进行明确处理。
- 暂不引入完整调用图、复杂 AST 服务、向量数据库或代码执行。

**验收：** 解析器测试覆盖有效/无效 Diff；事实统计来自解析器而非模型；路径和行号无法验证时不伪造；输入限制可稳定触发。

### 阶段 6：LangGraph 多 Agent 分析与结构化回调

**目标：** 把确定性事实转化为受约束、可校验的分析报告。

**工作项：**
- 按《Agent 工作流与证据规范》实现风险、影响、难度、测试建议和汇总节点。
- 通过统一模型适配层调用 DeepSeek API；Key 只从服务端配置读取。
- 设置每节点调用、单次请求超时、修正次数、总时限和 Token/费用预算。
- 结构校验器验证枚举、证据引用、路径、行号、报告大小和部分成功条件。
- Python 通过内部鉴权回调提交成功/部分成功/失败结果；Go 重新执行契约与当前尝试校验。

**验收：** 固定评测集可重复运行；无效证据不能通过校验；核心失败不伪装成部分成功；非核心节点失败可形成有明确限制的 `PARTIAL_SUCCESS`；模型 Key 不出现在前端或日志。

### 阶段 7：追问、手动重试与重新分析

**目标：** 完成用户真正会使用的任务后续流程。

**工作项：**
- 追问在接受时绑定具体报告、任务和线程；回复历史由 Go 持久化。
- 手动重试仅适用于符合条件的 `FAILED` 任务，最多 4 次，使用原任务 ID。
- 重新分析只接受终态任务，创建新任务并保存 `source_task_id`、`source_report_id` 和可选 `user_note`。
- 追问、重试和重新分析分别有独立幂等与并发控制。

**验收：** 普通追问不改变任务状态/执行次数；成功任务不可手动重试；未终态任务不能重新分析；新分析不覆盖旧报告；并发重试仅一个请求获得新尝试。

### 阶段 8：前端业务闭环

**目标：** 提供可演示、可检查的用户体验。

**工作项：**
- 登录/注册、Diff 提交与外部模型确认、任务列表/详情、状态展示、报告详情、证据引用、追问、手动重试、重新分析。
- 展示部分成功、失败原因、分析限制和重新分析关联。
- 对加载、空状态、超时、重复提交、权限失败和网络异常提供明确反馈。

**验收：** 真实前后端联调完成；页面刷新后任务/报告/对话仍可恢复；用户无法通过修改前端 ID 越权；关键流程不依赖手工改数据库。

### 阶段 9：安全、数据生命周期与部署检查

**目标：** 验证安全设计真正落地。

**工作项：**
- 验证日志脱敏、上传临时文件清理、数据保留清理、账号删除运维流程。
- 检查生产 Cookie/HTTPS/CORS、服务间鉴权、网络暴露、容器权限和密钥注入。
- 检查依赖漏洞与已知高风险默认配置。

**验收：** 《认证权限与安全设计》中的 MVP 验收清单逐项有测试或检查证据；未完成项明确标记，不得宣称已安全验收。

### 阶段 10：固定评测、故障测试与最终演示

**目标：** 形成能用于简历和面试的真实工程证据。

**工作项：**
- 固定 Agent 评测集，记录风险命中、误报、证据有效率、Hardness 一致性和模型失败情况。
- 执行 API、并发、数据库、Kafka/Celery 恢复与用户隔离测试。
- 记录 P50/P95、端到端耗时、错误率、队列等待、Token/费用和资源占用，并注明测试环境与样本量。
- 准备从提交 Diff 到查看报告、追问、失败重试、重新分析的演示脚本。
- 根据真实问题做一轮优化，再使用相同数据集和条件复测。

**验收：** 测试报告可复现；所有数字均有原始记录；优化前后差异如实呈现；未通过项和系统限制明确列出。

## 四、全局质量门禁

每个阶段完成前都需要：

- 变更文件清单与变更原因；
- 运行的测试命令及真实输出摘要；
- 失败测试和未解决问题；
- 对文档的偏差说明；
- 下一阶段是否具备准入条件。

禁止使用“代码已写完”“看起来没问题”作为验收结论。未执行的测试标记为“未运行”，不能标记为通过。

## 五、建议的实施顺序

建议严格按阶段 0→10 推进。阶段 3 可使用固定结果适配器验证 Go 业务闭环；阶段 4 证明异步可靠性后再接入真实模型；阶段 5 建立证据索引后再做 Agent；阶段 8 前端不提前扩展非必要页面。阶段间允许修复前一阶段发现的问题，但不跳过验收门。

## 七、文档与实现偏差管理

实施中如出现设计无法落地、依赖版本不支持或真实测试推翻假设，应提交一条偏差记录，包含：原设计、证据、影响范围、建议方案、是否影响其他文档。经确认后同步修改相关文档和测试。代码不能成为未经记录的“第二套规范”。

**完成状态：** 本文件定义实施顺序与验收要求。所有阶段仍待实际执行；当前没有任何阶段可以仅凭本文宣称通过。
