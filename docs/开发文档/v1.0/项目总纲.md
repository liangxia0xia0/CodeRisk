# CodeRisk 项目总纲

**文档版本：** V1.0（最终设计基线）  
**项目状态：** 最终设计基线已整理；尚未实现业务代码，下一步进入仓库现状检查与分阶段实施  
**项目定位：** 面向代码变更的风险评估与任务难度量化多 Agent 系统

## 一、项目简介

### 1.1 项目是什么

CodeRisk 是一个面向 Java、Python 代码变更的智能分析系统。

用户提交 Diff 文本或 Diff 文件后，系统提取代码变更及相关事实，结合静态分析与多 Agent 分析，生成可追溯的评估报告。用户可以查看结果，在同一对话中追问和质疑，也可以对符合条件的失败任务手动重试，或要求重新分析。仓库、Commit 和 PR 不是首版输入。

报告主要包含：

- **Risk：** 代码变更可能引入的风险、风险等级及其证据。
- **Hardness：** 任务的实现难度、复杂度及判断依据。
- **测试建议：** 需要重点验证的功能、边界条件和关联模块。
- **分析证据：** 支持评估结论的代码位置、分析结果和相关依据。

系统的目标不是让多个 Agent 自由聊天，而是建立一套具有明确业务流程、可验证结果和可复现评估能力的分析系统。

### 1.2 项目目标

项目需要同时满足以下目标：

1. **业务可用：** 完成从代码变更提交到评估报告生成的核心闭环。
2. **工程完整：** 具备前后端、认证、用户数据隔离、异步任务处理、持久化和部署能力。
3. **分析可信：** 尽可能让评估结论具有证据支持，能够检查和验证。
4. **技术合理：** 每项关键技术都对应明确的问题和设计理由。
5. **可量化验证：** 通过固定测试集、系统测试和优化前后对比，验证系统的实际表现。
6. **可持续扩展：** 为更多语言、分析工具、模型和 Agent 能力预留合理扩展空间。

### 1.3 项目目标不包括什么

首版不追求：

- 替代专业开发人员进行最终代码审查。
- 自动修改用户代码或自动合并代码。
- 执行用户任意提交的代码、构建脚本或测试脚本。
- 建设完整的企业级团队协作、组织管理和复杂多租户平台。
- 追求生产级系统的全部高可用、容灾和治理能力。
- 为展示技术而无实际业务价值地堆叠组件。

首版优先完成真实、可用、可演示、可测试的核心业务闭环。

## 二、设计原则

### 2.1 真实业务，最小实现

系统应按照真实业务需求设计，但实现范围保持克制。

所谓最小实现，是只实现满足当前业务目标所必需的能力，不是忽略基本安全、可靠性和工程规范。

### 2.2 先明确问题，再决定技术

技术选型必须说明：

- 当前要解决什么问题。
- 为什么选择这项技术。
- 是否存在更简单的替代方案。
- 引入后会增加哪些复杂度。
- 首版需要实现到什么程度。

不因为某项技术流行或有利于简历展示，就默认引入。

### 2.3 架构提前考虑，功能分阶段实现

总体设计需要提前考虑服务边界、数据流、异步任务、事件契约、失败恢复和扩展方向。

但是，提前考虑不代表所有能力都要在首版完整实现。每项能力都需要明确首版实现范围与后续扩展边界。

### 2.4 结果必须可以验证

系统输出不能只依赖模型的主观判断。

能够通过确定性程序提取的事实，应优先使用代码解析、静态分析和结构化数据获取。Agent 负责综合分析、推理和解释，并尽可能引用可验证的证据。

### 2.5 用户数据相互隔离

多个用户可以使用同一套系统和基础设施，但每个用户只能访问自己的对话、任务、报告和相关数据。

首版不建设复杂的团队协作体系。后端必须执行权限校验，不能只依赖前端隐藏数据。

### 2.6 安全与复杂度平衡

首版不执行用户任意代码，也不克隆仓库。仍需限制 Diff 解析和静态分析工具的资源消耗，隔离临时文件，并限制网络访问和进程权限。

安全措施应针对明确风险设计，不无限扩展为通用代码执行沙箱。

## 三、用户与业务范围

### 3.1 用户模式

- 支持邮箱注册与登录。
- 不支持手机号注册与登录。
- 用户独立使用系统，不能访问其他用户的对话、任务和报告。
- 认证方案采用短期 JWT Access Token 的 HttpOnly Cookie；MVP 不实现 Refresh Token 轮换。

首版认证和会话基线以《认证权限与安全设计》为准；邮箱验证、密码找回、Refresh Token 轮换等不属于 MVP。

### 3.2 核心业务流程

1. 用户确认 Diff 会发送给外部模型，并提交 Diff 文本或 Diff 文件。
2. 系统创建对话线程和第一个分析任务。
3. 系统提取 Diff、代码结构和能够安全获得的事实，并完成风险、难度和测试建议分析。
4. 系统保存任务状态、当前有效报告和对话。
5. 用户查看报告，继续追问或质疑。
6. 用户可以手动重试符合条件的失败任务，或在任务已经结束时要求重新分析。重新分析创建新任务并保留旧报告，可以附带可选补充说明。同一任务不会同时有两次未结束的业务执行。当前尝试若超过执行期限且确认无法继续恢复，以现有 `FAILED` 收口，不自动开始下一次业务执行。

任务状态、执行次数和报告规则见《数据库与任务状态设计》。本文件不另写一套状态机。首版不支持用户取消任务。下一次业务执行只由用户调用现有手动重试触发。Kafka 重投、Celery 恢复、模型内部重试、LangGraph 内部纠错和恢复扫描都不分配新的业务执行次数。

## 四、技术方向基线

以下为当前讨论形成的技术方向。具体版本、接口、部署参数和实现细节仍以正式技术设计为准。

| 层次 | 当前方向 | 主要职责 |
|---|---|---|
| 前端 | React、TypeScript、Vite、Ant Design、TanStack Query | 用户交互、任务管理、报告展示 |
| 业务后端 | Go、Gin、GORM、PostgreSQL | 认证、权限、业务规则、任务生命周期、报告持久化 |
| AI 服务 | Python、FastAPI、LangGraph | 代码分析、Agent 编排、分析结果生成 |
| 跨服务事件 | Kafka | 跨服务事件传递与异步协作 |
| Python 后台任务 | Celery、Redis | Python 内部后台任务执行与调度 |
| 部署与运维 | Docker、Docker Compose、Nginx | 容器化运行、反向代理与部署 |
| 代码分析 | Git Diff、AST、静态分析及依赖分析 | 提供可验证的代码事实 |

关键补充要求：

- Go 是业务状态和 PostgreSQL 的唯一权威。Python 不得直接写业务库，也不得自行分配业务执行次数。
- Kafka 传递跨服务事件，Celery 执行 Python 内部任务。二者都不是对话消息，也不能各自维护一套任务状态。
- 必须处理幂等、重复消费、当前执行恢复与用户手动重试的边界、回调校验，以及超时或中断后的失败收口。规则见数据库设计与接口契约。
- RAG、Embedding、Milvus、Tool、MCP、Context 和记忆机制需要在技术设计阶段逐项论证。
- 模型通过统一适配接口调用，初期使用 DeepSeek API，后续评估 Ollama 本地模型。
- 首版不默认引入所有候选技术。是否采用及采用到什么程度，必须记录决策依据。

## 五、测试与量化原则

测试是项目设计的一部分，而不是开发完成后的附加工作。

### 5.1 第一轮：MVP 基线测试

完成核心业务闭环后，建立第一轮完整测试基线，覆盖：

- Agent 分析能力与结果质量。
- API 正确性及并发性能。
- 数据库、缓存、任务队列与事件系统。
- 业务规则、认证、权限和用户数据隔离。
- 异步任务失败、重试、重复消费与恢复。
- CPU、内存、请求耗时、吞吐量和错误率。

测试结果必须保留测试数据、环境、参数和结果记录。

### 5.2 第二轮：优化后复测

根据第一轮测试发现的真实问题，选择有依据的优化措施。

优化后尽量使用相同测试集、环境和负载条件重新测试，比较优化前后的表现，并检查是否存在准确性下降、错误率上升或资源消耗增加等副作用。

### 5.3 结果真实性

项目不预先承诺未经验证的准确率、并发量或性能提升比例。

简历中使用的量化结果必须来自实际执行、可解释且可复现的测试。即使某项指标没有明显改善，也应如实记录。

## 六、项目设计文档体系

项目使用多份职责清晰、相互关联的文档，而不是把所有设计塞进一份超长 PRD。

| 文档 | 主要内容 |
|---|---|
| 项目总纲 | 项目基线、设计原则、文档导航、决策规则 |
| 产品需求与业务规则（PRD） | 用户场景、业务流程、功能范围、业务规则、验收标准 |
| 总体架构与技术决策 | 服务边界、技术选型、数据流、异步机制 |
| 数据库与任务状态设计 | 任务、线程、对话、尝试、报告的逻辑关系，状态机、重试和可靠性规则 |
| 系统接口与服务契约 | 对外 API、内部回调、Kafka 与 Celery 契约、错误码 |
| Agent 与代码分析设计 | Agent 分工、分析流程、RAG、工具、证据和评测 |
| 工程规范与实施计划 | 测试、部署、安全、可观测性、实施任务与验收 |

后续如某一部分复杂度明显增加，可以拆分专门文档，但必须维护清晰的导航和关联关系，避免重复维护同一份规则。

## 七、文档规范与决策追溯

### 7.1 文档基本要求

每份设计文档应根据自身职责包含：

- 文档目的与适用范围。
- 已确认的需求和设计。
- 关键设计理由与取舍。
- 必要的流程图、结构图或数据表。
- 关联文档与依赖关系。
- 验收标准。
- 未决事项。
- 变更记录。

不相关的章节不强行填充，避免为了格式完整而制造无效内容。

### 7.2 决策状态

所有关键设计应区分以下状态：

- **待讨论：** 尚未形成结论。
- **已确认：** 已经讨论并达成共识。
- **待验证：** 方案方向已确定，但仍需要通过实现或测试验证。
- **已变更：** 原有决策已被新的决策替代。

不能将待讨论事项写成已经确定的事实，也不能将待验证的假设写成已取得的结果。

### 7.3 需求追溯

重要需求应能够关联到后续设计和验证，例如：

需求 → 架构决策 → 数据模型 → API 或事件契约 → 实现任务 → 测试用例 → 测试结果。

这样，当需求变化时，可以判断哪些设计、代码和测试需要同步调整。

### 7.4 变更管理

如果实施过程中发现设计存在遗漏或矛盾，应记录问题及其影响。

涉及核心业务规则、技术架构、事件契约、数据模型或验收目标的变化，需要先说明原因与影响，再确认是否修改设计文档。

## 八、协作分工

### 8.1 设计与文档

由 ChatGPT 负责需求分析、技术方案、总体设计、文档编写和跨文档一致性检查。

设计过程中应优先使用已经确定的共识；确实需要新增决策时，说明原因、备选方案和影响。

### 8.2 业务决策

由项目发起人确认重要业务取舍，并逐步理解项目设计。

文档应以清晰、简洁、容易阅读为原则。复杂技术概念需要解释其作用，而不是只列技术名词。

### 8.3 工程实施

由 Cursor 对照已确认的设计检查实际仓库，拆分小任务、实施代码和执行验证。

Cursor 不应在没有说明的情况下擅自改变核心业务规则或架构。发现文档冲突、技术限制或实现障碍时，应先反馈，再确定处理方式。

### 8.4 实施边界

总体设计完成并通过一致性检查后，才进入按小任务逐步实施的阶段。

每个实施任务都应说明目标、允许修改的范围、非目标、验证方法和完成标准。通过一个任务的验收后，再推进下一项。

## 九、项目阶段与当前状态

项目按照以下顺序推进：

1. 产品需求与业务规则。
2. 总体架构与技术决策。
3. 数据库与任务状态设计。
4. 系统接口与服务契约。
5. Agent 与代码分析。
6. 工程规范、测试与实施计划。
7. 跨文档一致性审查。
8. Cursor 分阶段实施与验证。

当前状态：核心业务设计、Agent 工作流与证据规范、认证权限与安全设计和开发验收计划已形成文档基线，正在做最终跨文档核验。文档中的实现要求不代表代码已完成或测试已通过。首版默认限额、保留期限和超时参数以对应专项文档为准，部署后仍需按测试校准。

## 十、下一步

下一步按《开发实施与验收计划》从仓库基线检查和环境准备开始，完成每个阶段的验收后再进入下一阶段。实现时如发现设计与真实依赖不符，先记录差异、影响与修订建议，再同步更新文档，不得在代码中悄悄形成第二套业务规则。
