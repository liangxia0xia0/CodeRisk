## 一、产品概述

### 1.1 产品定位

CodeRisk 是一个面向 Java、Python 代码变更的风险评估与任务难度量化系统。

用户提交 Diff 文本或 Diff 文件后，系统分析本次变更，生成包含风险判断、任务难度、证据和测试建议的评估报告。用户可以查看结果，围绕原因、影响范围、证据和测试建议继续对话，也可以要求重新分析。仓库、Commit 和 PR 不是 MVP 输入。

CodeRisk 不以生成一段代码解释为最终目标，而是帮助用户回答三个实际问题：

1. **这次变更可能有什么风险？**
2. **这次任务有多难，难在哪里？**
3. **应该重点验证什么，才能降低变更带来的风险？**

系统的核心价值是把代码变更转化为结构化、可追溯、可验证的评估结果。

### 1.2 目标用户

首版主要面向以下用户：

- **开发人员：** 提交代码前，了解变更风险和需要补充的测试。
- **代码审查人员：** 在人工审查前，快速定位值得关注的变更及潜在影响。
- **技术负责人：** 辅助判断任务复杂度、影响范围和审查投入。

首版不建设复杂的团队协作与组织管理能力。上述用户均通过个人账号独立使用系统。

### 1.3 用户痛点

CodeRisk 主要尝试解决以下问题：

| 痛点 | 现有困难 | CodeRisk 的目标 |
|---|---|---|
| 变更风险难判断 | Diff 只能展示改了什么，不直接说明潜在影响 | 结合代码事实、依赖关系和分析结果识别风险 |
| 代码审查耗时 | 审查人员需要自行定位关联代码和关键路径 | 提供风险排序、代码位置与判断依据 |
| 测试范围难确定 | 开发者容易遗漏边界条件和关联模块 | 根据变更内容生成有针对性的测试建议 |
| 任务难度难评估 | 改动行数不能准确反映真实复杂度 | 结合依赖、影响范围、逻辑复杂度等因素评估 Hardness |
| AI 结论难验证 | 普通模型可能产生没有代码依据的推测 | 尽可能提供可定位、可核验的证据 |

以上为待验证的产品假设，不代表所有目标用户都已确认存在这些痛点。后续应通过真实案例与评测验证产品价值。

## 二、产品目标与成功标准

### 2.1 产品目标

首版需要完成以下目标：

1. 用户能够注册、登录并独立使用系统。
2. 用户能够提交支持范围内的代码变更分析任务。
3. 系统能够完成代码事实提取与风险、难度分析。
4. 系统能够生成结构化报告，并展示主要判断依据。
5. 用户能够查看自己的任务、对话历史、任务状态和历史报告。
6. 用户能够基于已有报告追问和质疑，并在需要时重新分析或对符合条件的失败任务手动重试。
7. 系统能够在分析失败或部分能力不可用时，正确记录状态并反馈问题。
8. 系统具备可重复执行的测试体系，能够评估分析质量与系统性能。

### 2.2 成功标准

产品是否成功，不仅看页面是否能够展示报告，还需要验证以下方面：

- **功能有效：** 核心业务流程能够完整运行。
- **结论有据：** 风险结论和关键建议能够关联到代码事实或其他明确证据。
- **分析有质量：** 在固定评测集上，风险识别和难度评估达到经过验证的基线要求。
- **系统可靠：** 异步任务、数据隔离、失败处理等关键流程通过测试。
- **性能可量化：** 能够测量请求延迟、任务耗时、吞吐量、错误率和资源使用。
- **优化可验证：** 优化前后可以在相同条件下进行对比。

具体数值目标不在缺乏基线的情况下凭空设定，而是在评测方案与测试环境确定后补充。

## 三、核心概念与业务规则

### 3.1 Risk：变更风险

Risk 表示本次代码变更可能引入的问题及其影响程度。

风险分析关注：

- 是否存在明显的逻辑缺陷或边界条件问题。
- 是否影响其他模块、接口或依赖组件。
- 是否可能破坏现有业务规则或数据一致性。
- 是否涉及异常处理、权限校验或安全边界。
- 是否存在缺少必要测试的关键路径。

风险等级用于帮助用户确定审查优先级，不等于缺陷必然发生的概率，也不等于系统能够证明代码存在真实 Bug。

每条重要风险应尽可能包含：

- 风险标题与描述。
- 风险等级。
- 涉及的代码位置。
- 相关证据。
- 可能的影响。
- 建议验证方式。
- 结论可信程度或证据充分程度。

风险等级固定为 `CRITICAL`、`HIGH`、`MEDIUM`、`LOW`、`INFO`。其含义、证据要求和结构校验规则以《Agent 工作流与证据规范》为准。首版不输出未经校准的缺陷概率分数。

### 3.2 Hardness：任务难度

Hardness 表示完成这项代码变更任务所需的技术理解、实现与验证工作量的相对难度。

它不等于 Risk，也不等于代码行数。

例如：

- 改动范围很小，但涉及复杂的并发状态管理，Risk 可能较高，Hardness 也可能较高。
- 修改范围较大，但主要是重复性的简单逻辑，Hardness 可能较高于小改动，但不一定存在高风险。
- 某项任务实现难度较高，但已有充分测试与明确设计，其 Risk 不一定同样高。

难度评估应考虑：

- 变更涉及的模块与依赖范围。
- 业务逻辑与控制流程的复杂程度。
- 接口、数据模型或兼容性变化。
- 并发、状态管理、异常处理等技术因素。
- 测试难度与验证成本。
- 对上下文、领域知识和跨模块理解的依赖程度。

报告需要说明难度判断的主要依据。首版 Hardness 等级固定为 `LOW`、`MEDIUM`、`HIGH`、`VERY_HIGH`，作为辅助决策指标，不是未经校准的精确工时预测；首版 `score` 固定为 `null`。具体输出契约以《Agent 工作流与证据规范》为准。

### 3.3 证据与结论

系统应区分三类信息：

1. **确定性事实：** 例如变更文件、Diff 行、语法结构、静态分析结果。
2. **分析判断：** 基于事实推导出的风险、影响或难度。
3. **待验证假设：** 需要运行测试、补充上下文或人工确认才能确定的结论。

不能把推测写成已证实的缺陷，也不能在缺乏证据时虚构代码位置或依赖关系。

如果分析证据不足，系统应明确提示不确定性，而不是为了生成完整报告而强行下结论。

## 四、用户使用流程

### 4.1 主流程

用户使用系统的基本流程如下：

1. 注册或登录。
2. 在提交前确认 Diff 会发送给外部模型。系统留存这次确认。
3. 提交 Diff 文本或 Diff 文件。系统创建对话线程和第一个分析任务。
4. 查看任务状态，直到分析进入终态。
5. 查看 Risk、Hardness、证据和测试建议。
6. 在同一线程中查看对话历史，追问原因、影响范围和测试建议，或质疑已有结论。
7. 对符合条件的失败任务手动重试，或要求重新分析。重新分析可以附带可选补充说明，并保留旧任务和旧报告。

继续对话、手动重试和重新分析是三种不同操作，详见 §4.4。用户不能取消已经提交的任务。系统不会因为超时、执行中断或基础设施恢复自动开始下一次业务执行。

### 4.2 任务状态

用户看到的任务状态与《数据库与任务状态设计》中的六种状态一致：

| 状态 | 用户可以理解的含义 |
|---|---|
| `PENDING` | 任务已接受，正在等待进入分析队列 |
| `QUEUED` | 已进入队列，等待本次业务执行 |
| `RUNNING` | 本次业务执行正在分析 |
| `SUCCEEDED` | 分析完成，报告可用 |
| `PARTIAL_SUCCESS` | 核心风险分析已完成，部分非核心分析没有完成。这是终态 |
| `FAILED` | 没有形成可用的核心分析结果 |

不向用户展示 `CANCELLED`、单独的“等待重试”或“正在恢复”状态。同一业务执行的排队、基础设施恢复和正常分析，仍显示为 `QUEUED` 或 `RUNNING`。

超过执行期限并经恢复判断确认无法继续的当前尝试，以及执行中断后确认无法按原 `attempt_no` 恢复的当前尝试，都进入 `FAILED`。发布或排队等待超过对应期限且无法恢复，也进入 `FAILED`。失败原因使用稳定错误码：运行阶段执行期限已到且无法恢复时为 `EXECUTION_TIMEOUT`；发布/排队无法恢复，或执行期限未到但当前尝试已中断且无法恢复时为 `EXECUTION_INTERRUPTED`。超出期限本身不等于立即判失败，恢复扫描必须先判断当前尝试是否仍可恢复。这些失败都不自动开始下一次业务执行。仍在有效期限或恢复判定窗口内的任务继续保持原状态。

`PARTIAL_SUCCESS` 必须标出哪些分析没有完成。系统不自动补跑这些项目。失败任务必须给出失败原因，不能显示成成功，也不能停在无法判断是否仍在运行的状态。前端是否允许重试，以任务查询返回的 `retry_allowed` 为准，不能自行用次数或状态猜测。

### 4.3 报告、证据与对话

用户打开自己的已完成任务后，应能够查看报告概要、详细分析和证据。

报告应区分确定性事实和 Agent 判断，支持用户从风险结论定位到相关代码位置或分析证据。

同一任务只有一个当前有效报告。历史任务上的报告继续可查看。新的分析结果不能无声替换旧报告。

在已有当前有效报告之后，用户可以追问或质疑。系统在接受这条消息时确定所讨论的任务和报告；用户也可以指定本线程中的一份历史报告。之后的回复只围绕这份报告，不把其他任务的结论当作当前事实，也不改写报告。追问不创建新任务，不消耗业务执行次数。回复可能成功，也可能失败；失败不影响任务状态和报告。若用户要求得到一次新的分析，必须走重新分析。

任务尚未产生当前有效报告时，用户仍可查看已经保存的对话和失败说明。此时不能生成一份新的分析结论。

报告是否支持导出、分享链接、批量分析等功能，首版不包含。

### 4.4 继续对话、手动重试与重新分析

| 用户操作 | 发生什么 | 历史如何保留 |
|---|---|---|
| 继续对话 | 线程和任务都不变，不增加执行次数，不创建分析任务 | 用户消息和 Agent 回复追加保存 |
| 手动重试 | 只用于 `retry_allowed` 为真的 `FAILED` 任务。用户调用现有手动重试后，Go 才分配下一次业务执行。每个任务最多 4 次 | 原任务保留。失败记录保留。成功后才产生该任务的当前报告 |
| 重新分析 | 源任务已成功、部分成功或失败时，在同一对话中创建新任务。可以附带可选补充说明。新任务重新读取原来的 Diff 并重新取证 | 旧任务和旧报告保留。新结果写入新任务。补充说明和前序报告只作为待验证参考 |

`SUCCEEDED` 和 `PARTIAL_SUCCESS` 没有手动重试。次数用尽、失败类型不允许重试，或任务仍有未结束的执行时，手动重试被拒绝并给出明确原因。正在等待或分析的任务不能重新分析。任务进入上述三种终态后，用户可以重新分析；其中只有失败类型允许重试且次数未用尽的 `FAILED` 才能手动重试。

失败回调、执行超时、恢复扫描和基础设施故障都不分配下一次业务执行。Kafka 重投、Celery 恢复、模型内部重试和 LangGraph 内部纠错只继续当前这一次执行，不显示为新的对话轮次。普通追问即使写了“重新分析”，也不创建任务。重新分析不自动带上历史对话中的全部消息。

仓库、Commit、PR 接入和用户取消都不是 MVP 功能。

## 五、代码输入与分析范围

### 5.1 首版支持的输入

MVP 只接受两种输入：

- 在请求中提交 Diff 文本。
- 上传 Diff 文件。

两种输入都规范化为该任务的一份 Diff。一个任务不更换输入。仓库、Commit 和 PR 接入属于后续扩展，首版必须拒绝，不能作为可选入口保留。

重新分析不要求用户再次上传。系统为新任务保存前序任务原始 Diff 的不可变副本，并重新提取事实和证据。旧任务的输入和报告保持不变。用户可以同时提交可选补充说明，接口字段名为 `user_note`；省略或空字符串表示没有补充说明。补充说明不改变原始 Diff。

### 5.2 语言范围

首版主要支持 Java 与 Python。

系统应识别无法解析、语言不支持、文件过大或输入不完整等情况，并向用户提供明确反馈。

不应把对两种语言的支持宣传为对所有项目结构、构建系统和复杂语法场景都具备同等分析能力。

### 5.3 分析范围

首版聚焦代码变更本身及其能够安全获取的相关上下文，包括：

- 变更文件与增删改内容。
- 代码结构与必要的 AST 信息。
- 可获取的模块、函数或依赖关系。
- 静态分析结果。
- 与变更相关的历史信息或项目知识（在相应能力得到确认后）。

首版不执行用户任意代码、构建脚本或测试脚本。分析过程中的文件解析和静态工具运行应具有资源限制和基本隔离。

## 六、报告需求

### 6.1 报告整体结构

一份完整报告至少应包括以下内容：

| 报告部分 | 用户需要了解什么 |
|---|---|
| 任务概要 | 分析了哪个变更，分析是否成功 |
| 变更概览 | 哪些文件和模块发生了变化 |
| 风险总览 | 主要风险、等级及审查优先级 |
| 风险详情 | 风险描述、代码位置、依据和潜在影响 |
| Hardness 评估 | 难度等级、关键影响因素及判断依据 |
| 测试建议 | 推荐测试的场景、边界条件和关联模块 |
| 分析限制 | 缺失上下文、无法解析的内容和结论不确定性 |

### 6.2 风险详情规则

每项重要风险应尽可能回答：

- 问题可能在哪里？
- 为什么认为它存在风险？
- 哪些代码事实支持这个判断？
- 可能造成什么后果？
- 应该如何验证？

如果系统无法给出充分证据，应降低结论可信程度或标记为待验证，而不是输出确定性断言。

### 6.3 Hardness 详情规则

难度报告需要说明影响难度的主要因素，例如跨模块影响、复杂逻辑、接口变化或测试成本。

不能只给出一个数字而不解释原因。

### 6.4 报告版本与可追溯性

每份当前有效报告都必须关联它所属的任务、生成它的那次业务执行，以及对应的 Diff。

重新分析是 MVP 的设计范围。它创建新任务和新报告，旧任务和旧报告仍然可以查看。同一任务不能出现两份同时生效的报告，也不能用新结论覆盖旧报告正文。前序报告和用户补充说明都不是新任务的已证实事实。

报告保存模型供应商/模型标识、提示词版本、实际耗时等必要诊断元数据；不得保存密钥或完整提示词。具体字段以《Agent 工作流与证据规范》和数据库设计为准。原始 Diff 到期清理后，历史报告仍可查看，但该任务不能再基于已删除的输入重新分析；用户需重新提交 Diff。

## 七、MVP 功能范围

### 7.1 首版必须实现

| 模块 | 最低要求 |
|---|---|
| 账号与认证 | 邮箱注册、登录及必要的令牌管理 |
| 用户隔离 | 用户只能访问自己的线程、对话消息、任务、输入与报告 |
| 外部模型确认 | 提交 Diff 前告知并取得确认，系统留存确认记录或审计事件 |
| 多轮对话 | 查看历史、追问原因和证据、质疑结论。普通追问不创建任务 |
| 任务管理 | 创建任务、查看状态和是否允许重试、对符合条件的失败任务手动重试、主动重新分析并可附带可选补充说明 |
| 代码输入 | Diff 文本和 Diff 文件两种方式都可用 |
| 代码事实提取 | 提取变更内容，并处理基本解析失败场景 |
| Agent 分析 | 形成有明确职责和结构化输出的分析流程 |
| 风险评估 | 输出 Risk、等级、证据与影响说明 |
| 难度评估 | 输出 Hardness、影响因素和判断依据 |
| 测试建议 | 输出与变更相关的验证建议 |
| 报告管理 | 保存当前有效报告和历史任务上的报告，禁止无声覆盖 |
| 异步处理 | 支持长时间分析任务，具备明确的状态与失败处理 |
| 基础可观测性 | 能够定位任务失败，并测量关键耗时与错误 |
| 自动化测试 | 为业务流程、权限、分析质量和系统可靠性建立测试基础 |
| 部署 | 提供可复现的容器化运行与演示方式 |

Kafka 是项目确定的技术方向，必须纳入总体架构和跨服务事件设计。首版具体采用哪些事件、消费链路如何闭环，在架构设计中确定。

### 7.2 首版不包含

- 仓库、Commit、PR 接入。
- 用户取消任务。
- 对 `SUCCEEDED` 或 `PARTIAL_SUCCESS` 的任务做手动重试。
- 自动补跑部分成功任务中失败的非核心分析。
- 跨任务自动学习和独立的长期记忆系统。
- 自动修复、修改或提交用户代码。
- 自动合并 PR。
- 任意用户代码、构建脚本或测试脚本的执行。
- 完整的团队、组织与协作权限体系。
- 企业级复杂审批与多租户管理。
- 无充分业务理由的多 Agent 自由讨论或无限循环。
- 为了技术展示而默认接入所有候选中间件、向量库和工具协议。
- 没有测试证据支撑的准确率、性能或可靠性承诺。

### 7.3 首版与扩展能力

首版应为扩展预留合理接口，但不能把所有未来能力都变成当前开发任务。

新增功能必须说明：

1. 解决什么业务问题。
2. 当前是否已有证据证明需要它。
3. 是否影响现有架构或数据模型。
4. 是否会增加维护和部署成本。
5. 是否值得纳入首版。

## 八、质量与验收标准

### 8.1 功能验收

MVP 至少需要证明：

- 用户可以完成注册、登录和退出后的重新登录。
- 用户可以提交 Diff 文本或 Diff 文件，并在确认外部模型使用后创建任务。
- 用户可以查看自己的任务状态、当前报告和同一线程的对话历史。
- 一条有效的代码变更能够走完整个分析流程。
- 报告包含 Risk、Hardness、证据与测试建议。
- 用户可以追问和质疑；该操作不创建新任务，也不改变当前报告。
- 符合条件的失败任务可以手动重试；成功和部分成功不能手动重试。前端以 `retry_allowed` 判断，次数用尽后该标志为否。
- 超时或中断且无法恢复时，任务进入 `FAILED` 并返回可区分的失败码，不自动出现下一次业务执行。仍在执行期限内的任务保持未结束状态。
- 用户可以在任务进入终态后重新分析，并可以提交可选补充说明。新任务可查看，旧任务和旧报告仍在。未结束的任务不能重新分析。若原始 Diff 已到期清理，接口返回 `SOURCE_INPUT_EXPIRED`，用户需重新提交 Diff；普通追问不创建任务。
- 无效输入、解析失败和分析失败能够得到正确反馈。
- 部分成功会标出未完成的非核心分析，并且不会自动补跑。
- 用户无法通过修改请求参数访问其他用户的线程、消息、任务和报告。
- 任务状态与实际执行结果一致。
- 关键结果和对话历史能够持久化，并在页面重新加载后查看。

### 8.2 分析质量验收

需要准备固定的代码变更评测集，覆盖典型风险、正常变更、复杂任务、边界条件和不应误报的场景。

每个评测案例应具有可检查的参考答案或评判规则。

根据评测结果，记录：

- 风险识别的准确性、召回情况与误报情况。
- 证据是否真实存在、位置是否正确。
- 风险解释是否与证据一致。
- Hardness 判断是否符合预先定义的评判标准。
- 测试建议是否覆盖关键场景。
- 不同运行之间的稳定性，以及模型调用失败时的处理情况。

不能仅依赖模型自我评分作为最终质量证明。必要时结合人工标注和确定性校验。

### 8.3 系统性能验收

需要设计独立的组件测试与完整业务链路测试。

至少记录：

- 并发请求数与请求成功率。
- 吞吐量和 P50/P95 延迟。
- 单个分析任务的端到端耗时。
- 队列积压与任务等待时间。
- 数据库连接池、查询耗时和资源使用。
- Kafka 生产、消费延迟与积压情况。
- Redis/Celery 的任务执行情况。
- CPU、内存和模型调用成本。

具体目标值应在测试环境、输入规模、模型服务和资源配置确定后制定，不能脱离测试条件单独宣称系统容量。

### 8.4 可靠性与安全验收

测试至少覆盖：

- 重复提交与重复消费。相同幂等键、不同内容会被拒绝。
- 手动重试使同一任务的业务执行累计不超过 4 次。服务重启、Kafka 重投、Celery 恢复和恢复扫描不增加次数。
- 失败回调、执行超时和基础设施故障都不分配下一次业务执行。并发手动重试只有一方成功。
- 基础设施重复投递不会新增业务执行或新任务。
- 过期回调不会覆盖当前报告。
- 任务状态与报告的一致性。
- 用户数据越权访问。
- 非法输入、过大 Diff 和异常解析内容。
- 外部模型服务超时、限流或不可用。
- 未确认外部模型使用时不能提交分析。
- Diff 文本和文件的大小、解析资源和临时文件限制。仓库克隆不在 MVP 验收范围内。

首版不要求达到完整生产级容灾标准，但不能忽略这些会影响基本可用性的风险。

## 九、测试与优化闭环

项目采用两轮完整测试，不预设一定能够获得某个优化比例。

### 第一轮：MVP 基线测试

完成 MVP 后，运行完整测试并记录基线：

1. 业务功能与权限测试。
2. Agent 固定评测集测试。
3. API 与并发压测。
4. 数据库、Redis/Celery、Kafka 相关测试。
5. 异步任务失败恢复测试。
6. 资源消耗、延迟与错误率测试。

测试结果用于发现真实问题，并确定优化优先级。

### 第二轮：优化后复测

针对第一轮证据明确的问题进行优化，再使用尽可能一致的环境、数据集和测试参数重新测试。

重点对比：

- 哪些指标发生变化。
- 变化幅度是多少。
- 哪个技术措施产生了改善。
- 是否引入了新的问题。
- 结果能否重复得到。

如果优化前后差异不明显，应如实记录，不制造结果。

### 简历证据要求

项目完成后，应能够从真实测试记录中提炼：

**业务问题或性能瓶颈 → 定位过程 → 技术改进 → 优化前后数据 → 改进效果与限制。**

简历中的所有量化数字必须有测试记录支撑。

## 十、已冻结规则与可配置参数

以下内容已在对应专项文档中完成设计。具体实现参数统一按下列基线执行；配置调整必须同步测试与文档。

| 事项 | 后续确认内容 |
|---|---|
| 代码输入 | 仅接受 Diff 文本和 Diff 文件；不支持仓库、Commit、PR。|
| 代码范围 | 默认限额：Diff 1 MiB、最多 500 个变更文件、增删行合计 20,000 行、解析时限 5 秒；服务端配置控制。|
| Risk / Hardness / 报告 | Risk 为 `CRITICAL/HIGH/MEDIUM/LOW/INFO`；Hardness 为 `LOW/MEDIUM/HIGH/VERY_HIGH`；证据和报告结构以《Agent 工作流与证据规范》为准。|
| 认证与安全 | 个人账号、短期 JWT HttpOnly Cookie；不要求邮箱验证、不实现密码找回、Refresh Token 轮换或用户自带 Key。|
| 异步架构 | 六种任务状态、HTTP 幂等、Outbox、消费去重、手动重试和超时收口规则已确认。|
| 执行期限 | 发布/排队等待 120 秒；运行期限 180 秒；恢复判定窗口 60 秒。均为可配置默认值，须通过故障测试校准。|
| Agent | 节点职责、失败降级与证据门禁以《Agent 工作流与证据规范》为准；不强制引入 RAG、向量数据库或 MCP。|
| 测试 | 固定评测集先建立基线，再优化复测；没有运行记录不得宣称指标达标。|
| 部署 | 首版以 Docker Compose 本地/演示环境为基线，生产部署另行配置 HTTPS、密钥与网络边界。|

输入限制、认证、安全、Agent 契约和异步参数均已有 MVP 默认基线；它们可依据真实测试调整，但不得由不同模块自行设定。RAG、Embedding、向量数据库和 MCP 不属于首版前置依赖。

## 十一、PRD 完成后的下一步

本 PRD 用于统一产品需求与业务规则。后续设计必须以此为基础，不应在技术设计中随意改变业务目标。
