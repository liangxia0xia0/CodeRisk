# CodeRisk——代码变更风险评估与任务难度量化平台

**文档版本：** V1.2（修订稿）  
**文档状态：** 待交叉审查；当前属于设计阶段，尚不能据此声称功能已实现或验收通过。  
**文档用途：** 项目入口，说明产品范围、目标架构、文档阅读顺序与当前进度。

## 1. 项目简介

CodeRisk 是一个面向 Java、Python 代码变更的 Web 评估平台。用户提交 Diff 文本或 Diff 文件后，系统提取可确认的变更事实，结合相关知识检索和 Agent 分析，生成结构化评估报告，帮助用户识别潜在风险、理解任务难度，并制定重点核查与测试建议。

系统强调**证据可追溯、推断有边界、结果可验证**：报告应区分 Diff 中直接可见的事实、由证据支持的判断，以及因缺少仓库上下文而无法确认的假设。

## 2. MVP 范围

### 当前设计范围

- 邮箱注册、登录、Access Token 与 Refresh Token，以及个人数据隔离。
- 提交 Diff 文本或 Diff 文件，对 Java、Python 语言内部的缺陷修复、功能变更和重构进行评估。
- 从风险、任务难度、证据、影响判断、测试建议和分析限制等方面生成报告。
- 查看任务状态、历史报告，并围绕已有报告继续对话。
- 对符合条件的失败任务进行手动重试；重新分析创建新任务并保留旧报告。
- 通过 RAG、Embedding、向量检索和受控 Agent Memory 提供有边界、可追溯的上下文。
- 记录必要的任务、尝试、报告、证据引用、事件和审计信息，支持故障恢复与测试评估。

### 明确不在 MVP 范围

- 上传或连接整个代码仓库、读取本地仓库、Commit/PR 集成。
- 完整调用链、全仓依赖图或仅凭 Diff 就声称已确认真实运行时影响。
- Java 与 Python 之间的跨语言迁移评估作为正式支持场景。
- 自动修改代码、生成并应用补丁、执行用户代码或测试、提交/推送/部署/合并。
- 复杂团队协作、组织权限体系、Kubernetes 等额外平台能力。

用户提交内容前，应明确告知 Diff 及必要上下文会发送给平台配置的外部模型服务，并取得确认。不得将原始 Diff、密钥或其他敏感内容写入普通日志。

## 3. 目标架构

```text
Web 前端
   │
   ▼
Go API ───────── PostgreSQL
   │                ├─ 业务数据与任务状态
   │                ├─ Transactional Outbox
   │                ├─ 知识与向量数据（pgvector）
   │                └─ 受控 Agent Memory
   │
   ▼
Kafka → Python 消费者 → Celery / Redis → LangGraph Agent
   ▲                                      │
   └──────────── 经鉴权的结果回调 ──────────┘
```

- **Go + PostgreSQL：** 身份、任务、尝试、报告、对话、审计与业务状态的权威来源。
- **Transactional Outbox + Kafka：** 可靠发布异步任务事件，避免业务事务成功但事件丢失。
- **Python FastAPI + LangGraph：** 执行 Agent 工作流、知识检索、证据组织与报告生成；不直接写业务数据库。
- **Celery + Redis：** Python 侧内部任务调度与执行，不作为业务状态的权威来源。
- **BGE-M3 + PostgreSQL/pgvector：** 当前计划采用的 Embedding 与向量检索方案；检索质量、向量维度、切分策略和资源开销仍需实际验证。
- **Nginx + Docker Compose：** 作为首版入口与本地/演示环境的部署方向，具体配置以实施和验证结果为准。
- **模型服务：** 首先接入 DeepSeek API；其他模型或本地推理方案需单独评估，不能预先视为已支持。

以上是目标设计，不是已部署架构。具体版本、参数、超时和资源限制以专项设计与后续验证为准。

## 4. 关键业务规则

- 一个任务对应一次 Diff 评估及其当前报告；重新分析会创建新任务，不覆盖历史报告。
- 每个任务最多分配 4 次业务执行尝试。只有初次执行和符合规则的手动重试会分配新的 `attempt_no`；消息重投和基础设施恢复不得增加业务尝试次数。
- 同一幂等键和相同请求内容应返回既有结果；同一幂等键对应不同内容时应返回冲突。
- 任务状态由 Go 侧业务数据控制。Python 回调必须经过鉴权，并校验任务、尝试和事件标识，防止旧回调覆盖新结果。
- 报告必须说明证据来源和分析限制；知识检索结果或历史记忆不能被当作本次 Diff 的直接事实。
- 不得把待验证的技术假设、设计参数或计划中的能力写成已经实现、已上线或已取得性能结果。

## 6. 开发与验收原则

1. **先核实仓库，再实施。** 先确认真实文件、依赖、启动方式和现有代码，不依据设计文档假设仓库已有实现。
2. **按小切片推进。** 每次实现一个可验证的业务闭环，并说明修改文件、非目标和验证命令。
3. **先建立基线，再优化。** 先执行完整基线测试，记录失败和性能数据；优化后在相同环境、相同数据集和相同测试条件下复测。
4. **同时验证功能与质量。** 除接口和状态流转外，还要评估 Agent 输出质量、证据准确性、并发吞吐、P95/P99 延迟、错误率、模型耗时与成本、数据库连接和慢查询、Kafka 积压、Celery 队列以及 CPU/内存。
5. **可观测但不泄露数据。** 使用关联 ID、结构化日志和关键指标追踪链路；普通日志不得记录原始 Diff、模型密钥或其他敏感数据。
6. **如实报告结果。** 只有实际执行并保留证据的测试才能标记通过；未运行的测试、未验证的性能和未实现的能力都必须明确标注。
