## 1. 文档目的

本文档定义 CodeRisk MVP 的数据库设计原则、核心实体、任务状态机、多轮对话关系、重试规则、异步处理一致性要求及数据生命周期。

本文档是任务状态、执行尝试、报告生效和可靠性规则的主要引用源。其他文档可以引用这里的规则，但不应重复定义或擅自修改任务状态、重试语义和数据关系。

本文档冻结业务关系和关键物理存储基线，不等同于已生成或执行的数据库迁移脚本。表名、字段语义、报告 JSONB 方案、证据关联原则、默认类型和期限作为 V1.0 设计基线；具体 SQL、索引与约束仍需在实施阶段生成并测试。下文用“已确认”表示必须遵守的业务规则，用“设计基线”表示默认实现，用“后续扩展”表示非 MVP 能力。

## 2. 已确认的设计决策

| 决策 | 当前结论 | 状态 |
|---|---|---|
| 分析输入 | 只接受 Diff 文本或 Diff 文件。不接受仓库、Commit、PR | 已确认 |
| Diff 存储 | 首版存储于 PostgreSQL；输入限额和保留期按《认证权限与安全设计》默认值执行 | 已确认 |
| 基础设施消息 | Kafka 在 Docker Compose 中真实运行，只传递跨服务事件 | 已确认 |
| 内部执行队列 | Python 使用 Celery + Redis | 已确认 |
| 业务状态来源 | Go 是业务状态和 PostgreSQL 数据的唯一权威。Python 不得直接写业务库 | 已确认 |
| 多轮对话 | MVP 必须支持线程、可追溯的对话历史，以及基于报告的追问 | 已确认 |
| 继续对话 | 不创建新 `task_id`，不增加 `attempt_no`。对话消息必须持久化 | 已确认 |
| 用户重新分析 | 仅当源任务已是 `SUCCEEDED`、`PARTIAL_SUCCESS` 或 `FAILED` 时，沿用现有重新分析接口创建新的 `task_id`。可选保存 `user_note`。保留旧任务、旧报告和历史记录 | 已确认 |
| 失败后手动重试 | 使用原 `task_id`。这是分配下一次 `attempt_no` 的唯一业务入口，只允许 `retry_allowed` 为真的 `FAILED` 任务 | 已确认 |
| 当前尝试的自动恢复 | Kafka 重投、Celery 恢复、模型内部重试、LangGraph 纠错和恢复扫描只接手原 `attempt_no`。失败回调不分配下一次 | 已确认 |
| 无法继续恢复的当前尝试 | 超过执行期限或执行中断且确认无法恢复时，用现有失败事务记为 `FAILED`。失败码区分 `EXECUTION_TIMEOUT` 与 `EXECUTION_INTERRUPTED` | 已确认 |
| 业务执行上限 | 每个任务最多 4 次。只有 Go 分配 `attempt_no`，且只在创建首个尝试和用户手动重试时分配 | 已确认 |
| 部分成功 | 核心风险分析成功、非核心分析失败时可为 `PARTIAL_SUCCESS`。该状态是终态，不自动补跑 | 已确认 |
| 风险与难度 | Risk/Hardness 等级、证据和报告结构以《Agent 工作流与证据规范》为准；首版不输出精确工时分数 | 已确认 |
| 外部模型隐私 | 提交前告知 Diff 会发送给外部模型，取得确认，并留存确认记录或审计事件 | 已确认 |
| 用户取消任务 | 支持取消未进入终态的任务；通过 Go 事务原子转换为 `CANCELLED` 并写入 Outbox | 已确认 |
| 任意代码执行 | MVP 不执行用户提交的代码、构建脚本或测试脚本 | 已确认的项目边界 |

业务执行次数按任务计算。第 1 次是创建任务时分配的初始执行，之后只能由用户手动重试再分配，因此一个任务最多有 4 个 `attempt_no`。Kafka 重投、Celery 恢复、模型内部重试、LangGraph 内部纠错和恢复扫描都不增加这 4 次。MVP 默认发布/排队等待期限 120 秒、运行期限 180 秒、恢复判定窗口 60 秒，配置位于 Go 服务配置并通过故障测试校准。

对话消息与 Kafka 事件、Celery 投递不是同一类对象。后文说“消息”时，会写明是对话消息还是基础设施消息。

## 3. 数据库设计原则

### 3.1 业务事实唯一

Go 后端负责业务规则和任务状态变更，PostgreSQL 保存权威业务状态。

Python Agent 服务不得直接写入业务数据库。分析结果、执行状态和失败结果均通过经过鉴权的内部接口提交给 Go 后端。

Kafka 消息、Celery 任务状态和 Agent 内存中的工作流状态都不能取代数据库中的业务状态。

### 3.2 用户数据隔离

所有用户可访问的线程、对话消息、任务、输入和报告必须能够追溯到所属用户。

- 用户只能查看和操作自己的线程、对话消息、任务和报告。
- 不允许仅凭前端传入的 `thread_id` 或 `task_id` 判定用户有访问权限。
- 报告读取、输入读取、对话读取、手动重试、重新分析和内部回调均需执行相应的身份或服务鉴权。
- 内部服务接口不能因不直接面向用户就跳过鉴权。
- 数据隔离必须通过后端业务校验实现，不能只依赖前端隐藏页面。

### 3.3 最小化持久化

只持久化业务流程需要的数据、对话历史、最终报告、必要的尝试记录、审计信息和可靠的基础设施消息处理信息。

对话历史是 MVP 业务数据，必须能够按线程检索和追加。除此之外，MVP 纳入受限的 Agent Memory：只保存经确认、允许复用且可追溯的信息，并执行用户隔离、状态校验与删除规则。Agent Memory 不等于自动学习所有历史对话，也不把 LangGraph 检查点当作业务事实来源。MVP 不预先建立通用工具调用数据库或团队协作数据库。

### 3.4 可恢复、可追溯

系统需要能够回答以下问题：

1. 任务是否已创建？
2. 分析请求是否已可靠发布？
3. 当前执行到哪一步？
4. 失败属于输入问题、模型问题还是基础设施问题？
5. 当前尝试是仍在正常执行、正在恢复，还是已确认无法恢复？失败码是什么？
6. 当前报告由哪次执行生成？
7. 哪些结论有证据，哪些分析未能完成？
8. 是否发生了重复消费、重复回调或过期结果覆盖？
9. 一条追问属于哪个线程，依据的是哪一份报告？
10. 一次重新分析继承了哪个线程和哪个前序任务？

## 4. 核心实体与关系

### 4.1 实体关系概览

```text
users
  └── threads
       ├── conversation_messages
       └── tasks
            ├── task_inputs
            ├── task_attempts
            │    └── reports（每个任务只有一个当前有效报告）
            │         └── report_evidence
            └── outbox_events

consumed_events
knowledge_documents
knowledge_chunks（BGE-M3 Embedding + pgvector）
agent_memories
audit_logs
```

上图是逻辑关系，不是物理表数量的决定。线程和对话消息必须能够独立于单次任务持久化；把它们塞进任务的单个状态字段，就无法保留同一对话下的多个任务和完整历史。是否拆成独立物理表、使用哪些列类型和索引，本轮不冻结。

### 4.1.1 已确认的对象关系

这些关系是业务规则：

1. `thread_id` 表示用户与 Agent 的一条对话及其持久化上下文。提交 Diff 时创建线程和第一个任务。
2. `task_id` 表示一次业务分析。一个任务只对应一份 Diff，输入形式是 Diff 文本或 Diff 文件。
3. 对话消息表示用户追问、质疑和 Agent 回复。它属于线程，不是 Kafka 事件，也不是 Celery 投递，也不等于分析任务。追问在被接受时必须保存目标 `task_id` 和 `report_id`。Agent 回复沿用这一绑定。普通追问不创建任务。
4. `attempt_no` 只编号同一任务的业务执行尝试，不编号对话轮次。编号从 1 开始，只有 Go 可以分配。
5. 报告是某次业务执行产生的分析结果。一个任务只有一个当前有效报告，并且必须追溯到生成它的 `attempt_no`。已被接受的报告不能被后续回调无声覆盖。
6. 继续对话不创建任务，也不增加 `attempt_no`。
7. 失败后的下一次业务执行只来自用户手动重试，留在原任务上，每个任务最多 4 次。每次新的业务执行使用新的 `event_id`。失败回调不分配这次执行。
8. 用户主动重新分析只允许源任务处于 `SUCCEEDED`、`PARTIAL_SUCCESS` 或 `FAILED`。此时创建新任务，旧任务、旧尝试、旧报告和对话历史都保留。源任务处于 `PENDING`、`QUEUED` 或 `RUNNING` 时不创建新任务。
9. 重新分析必须重新读取新任务自己的 Diff 并重新提取证据。旧报告和可选 `user_note` 只是待核查参考，不能直接当成事实。系统不把该线程的全部历史消息自动装入新任务。

同一线程下的任务成员关系，用来表示这些分析发生在同一段对话中。仅有成员关系还不够：新任务还必须知道自己依据的前序任务，否则无法区分“继续追问当前报告”和“要求基于某一次历史分析重新核查 Diff”。因此前序任务关联是必要的业务关系。逻辑字段与接口一致，使用 `source_task_id`、`source_report_id` 和 `user_note`。实现默认使用 PostgreSQL UUID 外键（如项目统一采用 UUID ID），`user_note` 使用 `TEXT` 并限制最多 2,000 个 Unicode 字符。`source_report_id` 仅在源任务已有当前有效报告时写入。

分析执行的 LangGraph 持久化状态按 `task_id` 与 `attempt_no` 隔离。对话上下文按 `thread_id` 和对话消息隔离。同一个 `event_id` 的重复投递只能对应同一次执行，不能写入另一个尝试或另一条线程的状态。LangGraph 检查点、Kafka 和 Celery 都不是业务状态的权威来源。

普通追问的模型上下文只包含当前这条用户消息、绑定同一 `report_id` 的历史对话、该报告及其证据；如需使用 Agent Memory，必须另行按用户归属、有效状态与相关性检索，并明确将其作为参考。其他任务的消息、报告和未经核实的旧结论不能当作当前事实。

### 4.2 核心表职责

| 实体 | 主要职责 | 状态 |
|---|---|---|
| `users` | 用户账号和认证关联 | 必须 |
| `threads` | 保存对话线程及当前分析上下文的归属 | 必须持久化；MVP 使用独立表 |
| `conversation_messages` | 按时间追加用户消息和 Agent 回复 | 必须持久化；MVP 使用独立表 |
| `tasks` | 保存任务当前业务状态 | 必须 |
| `task_inputs` | 保存该任务的一份 Diff | 必须。一个任务一份输入已确认；Diff 原文使用 `TEXT`，并以 `content_size` 约束字节上限 |
| `task_attempts` | 记录每次业务执行及失败、重试信息 | 必须 |
| `reports` | 保存任务的当前有效分析结果 | 必须。一任务一个当前有效报告已确认 |
| `report_evidence` | 保存报告结论对应的代码证据 | 必须；以报告发现关联证据 ID 的方式独立保存 |
| `outbox_events` | 可靠发布跨服务事件 | 必须 |
| `consumed_events` | 记录基础设施消费去重信息 | 必须；MVP 使用独立 `consumed_events` 表并对 `event_id` 建唯一约束 |
| `knowledge_documents` | 管理可供 RAG 检索的知识文档及来源、版本、状态 | 必须；纳入当前 RAG 设计范围 |
| `knowledge_chunks` | 保存文档切片、元数据和 BGE-M3 向量，供 PostgreSQL/pgvector 检索 | 必须；向量维度与索引配置须与所选模型版本一致 |
| `agent_memories` | 保存经过确认、可复用且带用户归属和来源的记忆 | 必须；不得跨用户读取，必须支持失效与删除 |
| `audit_logs` | 记录关键业务和安全操作 | 必须 |

### 4.2.1 RAG 知识数据与 Agent Memory

RAG 知识库与用户记忆是两类不同的数据，不得混存或共用不带权限边界的检索查询。

#### `knowledge_documents` 与 `knowledge_chunks`

- `knowledge_documents` 保存文档身份、标题、来源、版本、内容摘要、启用状态及创建/更新时间等管理元数据。
- `knowledge_chunks` 保存文档切分后的文本、所属文档、切片序号、来源定位信息、内容摘要、Embedding 模型标识和向量。
- Embedding 首选 **BGE-M3**；向量存储与相似度检索首选 **PostgreSQL + pgvector**，不默认引入 Milvus。
- 向量列的维度必须与实际部署的 BGE-M3 模型输出配置一致；模型版本或向量化配置变更时，应明确重建/迁移策略，不得将不同维度或不同配置的向量混合检索。
- 文档更新或停用后，检索必须遵守当前有效版本和状态；切片必须能够追溯到来源文档。检索结果作为上下文参考，不是当前 Diff 的直接证据。
- 知识文档的准入、更新、切分、重嵌入、检索过滤和评测流程由 Agent 工作流与实施文档进一步定义。不得把历史分析报告自动当作通用知识库内容。

#### `agent_memories`

建议字段至少包括：

| 字段 | 含义 | 设计要求 |
|---|---|---|
| `id` | 记忆唯一标识 | UUID |
| `user_id` | 所属用户 | 必须；检索和读取都要按用户过滤 |
| `memory_type` | 记忆类别 | 使用受控枚举，首版不开放任意类型 |
| `content` | 记忆内容 | 只保存最小必要、经确认的信息 |
| `source_task_id` / `source_report_id` | 来源任务/报告 | 能关联时必须保留来源 |
| `status` | 当前状态 | 至少区分有效、失效、删除/待清理状态 |
| `created_at` / `updated_at` | 创建与更新时间 | 使用带时区时间 |
| `expires_at` | 过期时间 | 可为空；按记忆类型配置 |

规则：

1. 未经确认的模型判断、普通对话全文和原始 Diff 不自动成为长期记忆。
2. 记忆不得跨用户访问；数据库查询必须包含用户归属条件，不能只依赖前端传入 ID。
3. 记忆召回时检查状态、归属和相关性；记忆不得覆盖当前 Diff 的事实。
4. 用户删除源数据或记忆时，按统一的数据删除与保留策略处理关联记录。
5. 记忆不属于任务状态来源，也不能用来恢复 `task_id`、`attempt_no` 或报告状态。
6. 首版不要求向量化所有记忆。是否将记忆也做向量检索，应由质量、隔离和延迟评测决定；即使复用 pgvector，也必须在检索查询中强制用户过滤。

### 4.3 `users`：用户表

职责：保存账号身份和认证所需的基础数据。

建议设计字段：

| 字段 | 含义 | 状态 |
|---|---|---|
| `id` | 用户唯一标识 | 设计基线 |
| `email` | 登录邮箱 | 冻结为 `email`，存储前按规则规范化并建立唯一索引 |
| `password_hash` | 密码哈希 | 设计基线 |
| `status` | 账号状态 | `ACTIVE`、`DISABLED` |
| `email_verified_at` | 邮箱验证时间 | MVP 不要求邮箱验证；字段可省略 |
| `created_at` | 创建时间 | 设计基线 |
| `updated_at` | 更新时间 | 设计基线 |

约束要求：

- 邮箱需要唯一性约束，并明确大小写归一化规则。
- 不得存储明文密码。
- Token 不应以明文形式写入普通业务记录。
- Refresh Token 的轮换、撤销和存储方式由认证安全设计专项冻结。

不在本表中预先加入组织、团队、部门等字段，因为 MVP 采用个人账号隔离模型。

### 4.4 `tasks`：分析任务表

职责：保存任务的当前权威状态和用户可见的任务信息。

建议字段：

| 字段 | 含义 | 状态 |
|---|---|---|
| `id` | 任务唯一标识，即 `task_id` | 设计基线 |
| `user_id` | 所属用户 | 必须 |
| `status` | 当前任务状态，只使用六种已确认状态 | 已确认 |
| `input_id` | 该任务唯一 Diff 输入的关联 | 使用 UUID 外键；一个任务关联一份输入 |
| `current_attempt` | 当前业务尝试序号，必须与尝试记录一致 | 作为 `tasks` 列保存，并与 `task_attempts` 在同一事务维护 |
| `failure_code` | 最终失败分类。稳定错误码以接口契约为准，至少区分 `EXECUTION_TIMEOUT` 与 `EXECUTION_INTERRUPTED` | 超时与中断两类已确认；其余码见接口契约 |
| `failure_summary` | 面向用户的简要失败说明 | 设计基线 |
| `created_at` | 创建时间 | 设计基线 |
| `started_at` | 首次开始执行的时间 | 首次进入 `RUNNING` 的时间；不因同一尝试恢复而重置 |
| `finished_at` | 任务进入终态的时间 | 设计基线 |
| `updated_at` | 最后更新时间 | 设计基线 |

约束要求：

- `user_id` 必须关联有效用户，任务也必须属于该用户的一个线程。
- 状态变更只能由 Go 执行。Python 不得直接更新任务。
- 更新任务状态时，应校验允许的迁移路径。
- `SUCCEEDED` 和 `PARTIAL_SUCCESS` 不得被手动重试或旧回调重新启动。
- 旧尝试的迟到回调不能覆盖新尝试或当前有效报告，也不能把已经按超时或中断收口的 `FAILED` 改回成功。
- `current_attempt` 若保存，必须与 `task_attempts` 中由 Go 分配的最大有效 `attempt_no` 一致。前端不能提交这个编号。

任务还必须能够关联其对话线程。重新分析产生的新任务还必须关联前序 `task_id`、可选 `user_note`，以及已有当前有效报告时的前序 `report_id`。这些关系使用 UUID 外键及 `TEXT` 型 `user_note`（最多 2,000 个 Unicode 字符），在创建新任务的同一个事务中写入。

是否增加 `retry_count`、`last_error_at` 或单独的调度时间字段，暂不冻结。应先确认这些信息能否由尝试记录可靠推导，避免重复存储相同事实。已用完的业务执行次数必须能够从尝试记录判断，不能只靠前端记忆。

### 4.5 `task_inputs`：分析输入表

职责：保存用户提交的 Diff 及分析所需的输入元信息。

建议字段：

| 字段 | 含义 | 状态 |
|---|---|---|
| `id` | 输入唯一标识 | 设计基线 |
| `task_id` | 关联任务。一个任务只有一份 Diff | 已确认 |
| `content` | Diff 原文 | PostgreSQL `TEXT`；应用层按 UTF-8 字节数校验 1 MiB 上限 |
| `content_hash` | 输入内容摘要 | 推荐 |
| `content_size` | 输入大小 | 推荐 |
| `source_type` | 文本输入或文件上传 | `TEXT`、`FILE` |
| `detected_languages` | 检测到的语言 | PostgreSQL `JSONB` 数组，内容为已支持语言标识；空数组表示未检测到 |
| `created_at` | 输入保存时间 | 设计基线 |
| `expires_at` | 计划清理时间 | 保留策略确定后冻结 |

约束与安全要求：

1. 在持久化前验证输入大小、格式和编码。
2. 限制单次 Diff 的最大字节数，防止超大请求耗尽资源。
3. 不将原始 Diff 写入普通应用日志、异常堆栈或追踪属性。
4. 通过任务归属校验控制输入读取。
5. 原始输入的保留时间应有明确规则；到期清理应可重试、可审计。
6. 不默认永久保存所有用户提交的代码。
7. 用户提交前必须明确知晓 Diff 将发送给外部模型，并完成相应确认。确认记录或审计事件必须留存，不能只在页面上提示一次而不保留。
8. 同一线程中的后续追问和重新分析仍会把该 Diff、相关报告或对话上下文发送给外部模型。已留存的确认必须能够覆盖这些后续调用；不能在对话阶段变成未经记录的外发。

一个任务对应一份 Diff 是已确认的业务规则。重新分析创建新任务和新的输入记录，内容来自前序任务的原始 Diff，但不能和旧任务共用一份可被改写的输入。`user_note` 不写入 Diff，也不改变旧输入。文件上传后的标准化算法、摘要算法和具体列类型在迁移实现时确定。原始 Diff 到期清理后，该任务仍可查看历史报告，但不允许基于已删除的输入重新分析；如需重新分析，用户必须重新提交 Diff 并创建新任务。

### 4.6 `task_attempts`：执行尝试表

职责：记录每次实际执行，区分任务的业务生命周期与某次执行的结果。

建议字段：

| 字段 | 含义 | 状态 |
|---|---|---|
| `id` | 尝试记录唯一标识 | 设计基线 |
| `task_id` | 所属任务 | 必须 |
| `attempt_no` | 尝试序号 | 必须 |
| `status` | 当前尝试状态 | 固定为 `PENDING`、`RUNNING`、`SUCCEEDED`、`PARTIAL_SUCCESS`、`FAILED` |
| `started_at` | 本次开始时间 | 设计基线 |
| `finished_at` | 本次结束时间 | 设计基线 |
| `failure_code` | 失败分类 | 使用《系统接口与服务契约》的错误码；成功时为空 |
| `failure_detail` | 受控诊断信息 | `TEXT`，仅保存脱敏后的受控诊断摘要，禁止保存 Diff、密钥和完整模型请求 |
| `trace_id` | 关联分布式追踪 | 推荐 |
| `created_at` | 记录创建时间 | 设计基线 |

约束要求：

- 同一任务的 `attempt_no` 必须唯一，并且只能由 Go 分配。
- 第一次业务执行在创建任务时记为 1。之后只有用户手动重试在同一任务上递增，总数不超过 4。失败回调不递增。
- 用户重新分析和继续对话都不增加原任务的 `attempt_no`。
- 允许手动重试的失败码见接口契约。输入无效等确定性错误记为 `FAILED` 后不接受手动重试。
- Kafka 重投、Celery 恢复、模型调用内部重试、LangGraph 内部纠错和恢复扫描不得新增尝试记录，也不得新建任务。
- 单次尝试超过执行期限，不表示可以自动开始下一次业务执行。Go 先判断该尝试是否仍在正常执行或仍可恢复；确认无法继续时，用失败事务收口为 `FAILED`。默认执行期限 180 秒，恢复判定窗口 60 秒。
- 重试不能把已有当前有效报告换成另一份，也不能重复触发不可幂等的业务操作。

任务状态不使用 `RETRY_WAIT`。尝试状态固定为 `PENDING`、`RUNNING`、`SUCCEEDED`、`PARTIAL_SUCCESS`、`FAILED`。创建尝试时为 `PENDING`，确认开始执行后转为 `RUNNING`，结束后转为对应终态；尝试状态不能与任务六态互相矛盾。

### 4.7 `reports`：分析报告表

职责：保存某次分析生成、能够被用户读取的结构化报告。

建议报告至少包含：

- 风险等级、理由和证据关联。
- 任务难度等级、理由和证据关联。
- 影响分析。
- 测试建议。
- 已完成与未完成的分析项目。
- 已知限制及不确定性。
- 分析所用模型和必要的版本元信息。
- 报告生成时间及其对应的执行尝试。

建议字段：

| 字段 | 含义 | 状态 |
|---|---|---|
| `id` | 报告唯一标识 | 设计基线 |
| `task_id` | 所属任务 | 必须 |
| `attempt_id` | 生成该报告的尝试 | 必须关联来源尝试 |
| `status` | 与创建该报告的任务终态一致，只能是 `SUCCEEDED` 或 `PARTIAL_SUCCESS` | 独立列设计基线 |
| `report_data` | 结构化报告主体 | JSONB 设计基线 |
| `created_at` | 报告生成时间 | 设计基线 |

约束要求：

- 报告必须能够追溯到任务和具体 `attempt_no`。
- 一个任务只有一个当前有效报告。核心风险分析没有成功完成时，不得保存伪装成完整成功的报告。
- 非核心分析失败时，可以产生 `PARTIAL_SUCCESS` 报告，但必须明确标记缺失项和限制。MVP 不自动补跑这些失败项，也不允许通过手动重试接口重新执行该任务。
- 同一尝试重复提交结果时，按 `task_id`、`attempt_no` 和 `event_id` 幂等处理，不生成第二份当前有效报告。
- 用户主动重新分析时，新任务生成自己的报告，不覆盖旧任务的报告。
- 失败尝试的诊断记录保留。已接受的报告不能被原位改写或删除来“更新结论”。
- 对话回复和 Kafka、Celery 的基础设施重试都不能改变报告的业务结果。

报告主体使用 PostgreSQL `JSONB` 保存结构化报告；`task_id`、`attempt_id`、报告状态与创建时间作为独立列，以支持归属、状态校验和关联查询。风险/难度枚举与报告 JSON 契约以《Agent 工作流与证据规范》为准。不引入多份同时生效的报告版本。

### 4.8 `report_evidence`：报告证据表

职责：把分析结论与实际代码变更建立可追溯关联。

建议字段：

| 字段 | 含义 | 状态 |
|---|---|---|
| `id` | 证据唯一标识 | 设计基线 |
| `report_id` | 所属报告 | 必须 |
| `finding_id` | 对应分析结论的稳定 ID | 必须与报告 JSON 中的 `finding_id` 对应 |
| `file_path` | Diff 中的文件路径 | 推荐 |
| `start_line` / `end_line` | 可核验的行范围 | 可空；无法定位时不得编造 |
| `source_ref` | 对应解析器事实/hunk 的内部引用 | 必须指向本次输入的事实索引；不复制整段 Diff |
| `evidence_type` | 证据类别 | 使用 Agent 规范枚举 |
| `explanation` | 证据说明 | 设计基线 |

约束要求：

- 证据应指向本次输入中的具体变更，不能凭空生成文件路径或行号。
- 当行号无法可靠确定时，应明确标记不可定位，而不是编造精确位置。
- 证据必须能关联到具体结论，不能只有孤立的代码片段。
- 没有充分证据的结论应标注不确定性。
- 不应把整个 Diff 无差别复制到每条证据记录中。

**设计基线：** 保留独立 `report_evidence` 表，便于证据关联、约束和查询；报告 JSONB 中保留完整结构化视图。`finding_id` 关联报告内稳定的发现 ID，证据类型与字段语义以《Agent 工作流与证据规范》为准。不得在报告和证据表中重复存储整份 Diff。

### 4.9 `outbox_events`：事务 Outbox 表

职责：确保业务事务成功后，对应的跨服务事件不会因为进程崩溃而永久丢失。

建议字段：

| 字段 | 含义 | 状态 |
|---|---|---|
| `id` | Outbox 记录标识 | 设计基线 |
| `event_id` | 全局事件唯一标识 | 必须 |
| `aggregate_type` | 业务实体类型 | 推荐 |
| `aggregate_id` | 业务实体标识 | 推荐 |
| `event_type` | 事件类型 | 首版必需 `analysis.requested`、`conversation.reply_requested` |
| `payload` | 最小事件载荷 | JSONB；只存标识和调度信息，不存 Diff/对话正文/报告 |
| `created_at` | 创建时间 | 设计基线 |
| `published_at` | 成功发布确认时间 | 设计基线 |
| `publish_attempts` | 发布尝试次数 | 推荐 |
| `last_error` | 最近发布错误摘要 | `TEXT`，保存脱敏后的错误码/摘要，不保存消息正文或密钥 |

处理规则：

1. 创建任务与创建 Outbox 事件必须在同一个 PostgreSQL 事务中完成。
2. 发布器从 Outbox 读取待发布事件，并发送至 Kafka。
3. 发布成功后更新对应记录。
4. 如果发布成功但更新数据库前进程崩溃，允许重复发布；消费端必须幂等。
5. 发布失败不能直接丢弃事件。
6. 事件载荷不携带完整 Diff 或完整报告，原则上只携带任务标识、尝试序号、事件 ID 等必要信息。
7. Outbox 的清理周期、最大重试时间和长期失败告警机制需在部署与可观测性设计中冻结。

### 4.10 `consumed_events`：消费幂等记录

职责：防止 Kafka 重复投递导致重复调度、重复执行或状态被重复推进。

建议至少记录：

- 消费者身份。
- `event_id`。
- 处理状态。
- 接收与处理时间。
- 必要的错误信息。

同一消费者的同一事件应具有唯一约束或等价的原子去重机制。

这里有一个必须在实现前解决的边界：**先把事件记为已消费，再将任务提交到 Celery，如果进程中途崩溃，可能导致任务丢失。** 因此不能只做简单的“插入去重记录后立即提交 Kafka offset”。

推荐先实现具备恢复能力的消费流程：保证事件到内部任务队列的投递可靠，只有在内部任务已可靠接收后才确认 Kafka 消费位点；如果仍存在跨系统提交窗口，则依靠幂等、重投与恢复扫描弥补。具体实现方式在异步处理专项冻结。

首版使用独立 `consumed_events` 表，以 `(consumer_name, event_id)` 唯一约束去重，并记录 `RECEIVED`/`ENQUEUED` 状态；恢复扫描处理长期停留在 `RECEIVED` 的事件。Kafka Offset 只在 Celery 可靠接收后提交。

### 4.11 `audit_logs`：审计日志表

职责：记录影响数据安全、任务结果和业务可追溯性的关键操作。

首版建议覆盖：

- 登录与认证相关安全事件。
- 创建分析任务。
- 读取或下载敏感输入与报告的必要审计事件。
- 手动重试、次数耗尽，以及执行超时或执行中断收口。
- 分析完成、部分成功与失败。
- 用户触发的重新分析。
- 管理或内部服务执行的关键状态变更。

日志应记录操作者、操作类型、关联资源、结果与时间。

不记录密码、Token、原始 Diff、完整对话正文或模型 API 密钥。

首版审计至少还要能证明：用户在提交 Diff 前已确认该内容会发送给外部模型。实现上可以是确认记录或审计事件，二者择一即可，不因此冻结一张新的物理表。同一确认必须能关联到对应线程和任务，供后续追问与重新分析追溯。

审计事件的详细字段、保留期限和是否对用户展示，属于安全设计专项，本轮不冻结。

### 4.12 线程与对话消息

线程保存一条对话的归属、创建时间和它与任务的成员关系。对话消息按发生顺序追加，至少要能区分用户与 Agent、保存正文、记录时间。追问消息必须保存接受时确定的 `task_id` 和 `report_id`。消息使用独立 `conversation_messages` 表；正文使用 `TEXT`，角色使用 `USER`、`ASSISTANT`、`SYSTEM` 固定枚举；追问接受时必须保存绑定的 `task_id` 与 `report_id`。

已确认的持久化要求：

- Go 在同一个 PostgreSQL 事务中写入用户追问、对应 Outbox，并确定目标 `task_id` 与 `report_id`。请求若带本线程内的 `report_id`，就绑定该报告及其任务；否则绑定线程中已有当前有效报告里、所属任务创建时间最新的一份。事务提交后，Worker 不得改选目标。
- 没有可绑定的当前有效报告时，不生成分析性回复。已保存的历史仍可查询。
- 普通追问不创建任务，不分配 `attempt_no`，也不修改当前有效报告。
- 对话回复有三种逻辑结果：等待、完成、失败。这是消息上的处理结果，不是新的任务状态，也不要求单独的表。
- 回复回调以原来的 `event_id` 幂等。重复回调返回已保存的回复，不追加第二条。
- 模型内部重试耗尽后，把该次回复记为失败。任务状态、`attempt_no` 和报告保持不变。用户可以再发送一条新消息。
- 检查点显示完成但数据库还没有回复时，只能用原 `event_id` 重新提交回调。数据库已有回复时，不再执行该次图，也不再追加回复。
- Agent 回复沿用用户消息上的 `task_id` 和 `report_id`，只追加对话。
- 用户要求重新分析时，必须调用现有重新分析接口，且源任务已经处于 `SUCCEEDED`、`PARTIAL_SUCCESS` 或 `FAILED`。Go 在同一事务中创建新任务、保存可选 `user_note`、关联前序 `task_id` 与前序 `report_id`（若已有当前有效报告），并在原线程保留历史。普通对话文本不触发这次创建。新任务的分析输入不是全部历史消息。

LangGraph 如果持久化分析过程状态，检查点键必须包含 `task_id` 和 `attempt_no`。如果持久化某次追问的执行状态，检查点键必须包含 `thread_id` 和该次对话事件标识，且不得与分析检查点混用。重复投递只能命中原来的检查点。这些检查点可以丢弃或按执行周期清理；业务消息和报告仍以 Go 写入的 PostgreSQL 数据为准。

不在本轮决定消息正文的列类型、分页游标、检查点存储介质和保留天数。

## 5. 任务状态机

### 5.1 任务状态定义

| 状态 | 含义 | 终态 |
|---|---|---|
| `PENDING` | 任务已创建，等待可靠发布请求 | 否 |
| `QUEUED` | 分析请求已可靠发布，等待执行 | 否 |
| `RUNNING` | 分析正在执行 | 否 |
| `SUCCEEDED` | 核心及规定的非核心分析均完成 | 是 |
| `PARTIAL_SUCCESS` | 核心风险分析完成，但部分非核心分析失败 | 是 |
| `FAILED` | 核心风险分析未能完成或任务无法形成可用报告 | 是 |

这七种状态是已确认的任务状态全集。`SUCCEEDED`、`PARTIAL_SUCCESS`、`FAILED`、`CANCELLED` 是终态。任务不包含任务级 `RETRY_WAIT` 或“正在恢复”。等待下一次业务执行时仍使用 `QUEUED`；该迁移只发生在用户手动重试成功之后。同一尝试的恢复不改变任务状态，也不增加 `attempt_no`。

### 5.2 合法状态迁移

```text
PENDING
  ├── CANCELLED（用户取消）
  ├── QUEUED
  └── FAILED（确定性入队错误，或发布等待超过配置期限且无法恢复）

QUEUED
  ├── CANCELLED（用户取消）
  ├── RUNNING
  └── FAILED（排队超过配置期限且无法恢复，或请求无法恢复地失效）

RUNNING
  ├── CANCELLED（用户取消）
  ├── SUCCEEDED
  ├── PARTIAL_SUCCESS
  └── FAILED（当前尝试失败、执行超时，或执行中断且无法恢复）

FAILED
  └── QUEUED（仅用户手动重试；失败类型允许、次数未用尽、没有未结束尝试）
```

`SUCCEEDED`、`PARTIAL_SUCCESS`、`FAILED` 和 `CANCELLED` 都是终态，没有向外的迁移。`PENDING`、`QUEUED`、`RUNNING` 可在取消事务成功时转为 `CANCELLED`。继续对话不改变任务状态。不存在 `RUNNING → QUEUED` 的自动迁移。

补充规则：

- 失败回调只结束当前尝试并把任务记为 `FAILED`，不在同一事务中分配下一次执行。
- 手动重试只能在任务已经是允许重试的 `FAILED` 时，由另一个事务分配下一个 `attempt_no`。并发的第二个手动重试不分配编号。
- 基础设施重投、恢复扫描和 LangGraph 内部纠错不能触发新的业务执行迁移。
- 终态成功或部分成功的任务不接受旧事件或手动重试回到执行状态。
- 用户重新分析只在源任务已终态时创建新任务，新任务从 `PENDING` 开始。这不是原任务的状态迁移。非终态源任务保持原状态，不产生新任务。
- 用户可以取消未进入终态的任务。Go 在事务中执行条件状态更新并写 Outbox；只有当前状态仍为 `PENDING`、`QUEUED` 或 `RUNNING` 时才可成功转为 `CANCELLED`。若完成事务先提交，取消返回当前终态；若取消事务先提交，后续完成/失败回调不得覆盖 `CANCELLED`。
- 状态迁移由 Go 在数据库事务中完成，不能只依赖 Python Worker 自觉遵守。

### 5.3 核心分析与部分成功

核心风险分析是形成有效分析报告的必要条件。

| 执行结果 | 任务结果 | 处理方式 |
|---|---|---|
| 核心风险分析成功，所有规定分析完成 | `SUCCEEDED` | 保存完整报告 |
| 核心风险分析成功，部分非核心分析失败 | `PARTIAL_SUCCESS` | 保存部分报告并标记缺失项。不自动补跑，也不接受手动重试 |
| 核心风险分析失败 | `FAILED` | 结束当前尝试并保留失败码。不分配下一次 `attempt_no`。只有失败码允许且次数未用尽时，用户才能手动重试 |
| 输入格式错误、Diff 无效等确定性问题 | `FAILED` | 失败码不允许手动重试 |
| 模型临时不可用、模型调用超时、可恢复限流 | `FAILED` | 先耗尽当前尝试内部重试。仍失败则收口，不自动开始下一次业务执行 |
| 已进入 `RUNNING` 且执行期限已到，当前尝试无法继续 | `FAILED` / `EXECUTION_TIMEOUT` | 失败事务收口。同时发生中断时仍用该码。不分配下一次 `attempt_no` |
| 发布或排队无法继续，或期限未到但执行已中断 | `FAILED` / `EXECUTION_INTERRUPTED` | 失败事务收口。不分配下一次 `attempt_no` |
| 四次业务执行仍未形成可用核心分析结果 | `FAILED` | 保留失败原因和尝试记录。再次手动重试必须被拒绝 |

核心风险分析的精确定义、最低证据要求和成功判定条件，应由《Agent 工作流与证据规范》补充，但不得与本文档的部分成功规则冲突。

### 5.4 状态更新与并发控制

同一任务最多只有一个未结束的业务执行。`PENDING`、`QUEUED` 和 `RUNNING` 都表示当前尝试尚未结束。

Go 只有在创建任务或接受手动重试时分配 `attempt_no`。手动重试必须在同一个 PostgreSQL 事务中重新检查任务状态、失败码和已用次数，确认没有未结束尝试，然后再写入新尝试、把任务改为 `QUEUED` 并保存 Outbox。竞争失败的一方不得分配新编号，也不得写入新的 Outbox。`(task_id, attempt_no)` 唯一约束只作为最后保护，不能代替事务里的状态检查。

失败回调和恢复扫描的失败事务只结束当前尝试并把任务改为 `FAILED`。它们不写入新的尝试，也不发布下一次 `analysis.requested`。

事务内的判定：

- 失败回调：仅当回调匹配当前 `attempt_no`，且任务仍处于允许接收该失败的未结束状态。同一事务结束该尝试并写入 `failure_code`。不分配下一个编号。`EXECUTION_TIMEOUT` 与 `EXECUTION_INTERRUPTED` 不接受来自 Python 的原值；Python 传入时改记为 `ANALYSIS_FAILED`。这两个码只由恢复扫描写入。
- 手动重试：仅当任务已经是允许重试的 `FAILED`、没有未结束尝试且 `attempt_count` 小于 4。并发的另一个手动重试返回冲突。
- 旧尝试或已经收口的尝试若再收到成功或失败回调，拒绝该回调，不再分配下一次。
- Kafka 重投和 Celery 恢复只接手已有 `event_id`，不进入编号分配。

因此需要同时防止：

- 同一个任务存在两个未结束尝试，或被两个 Worker 同时执行。
- 旧尝试迟到的回调覆盖新尝试，或把已收口的失败改写成成功。
- 同一个事件被重复消费后创建多个执行任务。
- 已完成的任务因重复消息重新执行。
- 两个并发手动重试分配出两个不同的新编号。
- 超时、恢复扫描或基础设施故障直接写出下一个 `attempt_no`。

MVP 使用 PostgreSQL 条件更新并结合事务/唯一约束实现并发保护；需要读取并决策当前状态时使用行级锁。默认发布/排队等待期限 120 秒、执行期限 180 秒、恢复判定窗口 60 秒；不得靠缩短期限绕过“一个未结束尝试”和唯一编号，也不能把仍在有效恢复窗口内的尝试提前收口。

恢复扫描复用现有任务、尝试、Outbox 和失败事务，不新增任务状态、服务或队列。按下面的顺序判断，不能只因为任务耗时较长就收口：

1. **仍在正常执行：** 当前尝试未结束，也没有中断，并且尚未超过 Go 服务配置中的对应期限。进入 `RUNNING` 之后使用执行期限；尚未进入 `RUNNING` 时使用发布或排队等待期限。扫描器不改状态，不分配新编号。
2. **正在恢复：** 同一 `attempt_no` 的 Outbox 重发、Kafka 重投或 Celery 恢复尚未结束，且仍在 60 秒默认恢复判定窗口内（可配置）。任务保持原来的 `PENDING`、`QUEUED` 或 `RUNNING`。这不是新的业务执行。
3. **已确认无法恢复：** 原尝试已经不能继续。只有完成恢复判定后才进入失败事务，不分配下一个 `attempt_no`。失败码按下面的规则二选一：
   - 尝试已经进入 `RUNNING`，且执行期限已到：`EXECUTION_TIMEOUT`。即使同时发生中断，也使用这个码。
   - 发布或排队等待期限已到，或者期限未到但执行已中断且无法按原 `attempt_no` 恢复：`EXECUTION_INTERRUPTED`。

收口后，迟到回调按过期回调拒绝。用户之后只能按现有手动重试或重新分析规则处理终态任务。默认期限分别为发布/排队等待 120 秒、执行 180 秒、恢复判定 60 秒；配置键名在 Go 配置中统一使用 `TASK_QUEUE_WAIT_TIMEOUT`、`TASK_EXECUTION_TIMEOUT`、`TASK_RECOVERY_WINDOW`。

## 6. 重试规则

### 6.1 可手动重试与不可手动重试

当前尝试内部可以先处理暂时性故障。内部处理耗尽后，任务进入 `FAILED`，不自动分配下一次业务执行。

创建请求在落库前被拒绝时，不留下任务，也不占用 `attempt_no`。这包括未确认外部模型，以及直接拒绝的 `INPUT_TOO_LARGE`。`INVALID_INPUT` 和 `UNSUPPORTED_LANGUAGE` 若在任务已经创建后才确定，则把该任务记为 `FAILED`，并且不允许手动重试。

**进入 `FAILED` 后仍允许手动重试的失败码：**

- `EXECUTION_TIMEOUT`
- `EXECUTION_INTERRUPTED`
- `MODEL_TIMEOUT`
- `MODEL_UNAVAILABLE`
- `RATE_LIMITED`
- `ANALYSIS_FAILED`
- `INTERNAL_ERROR`

**进入 `FAILED` 后不允许手动重试的失败码：**

- `INVALID_INPUT`
- `INPUT_TOO_LARGE`
- `UNSUPPORTED_LANGUAGE`
- `RESULT_INVALID`
- 其他确定性业务错误

用户权限错误和请求参数错误若发生在创建任务之前，不创建任务。具体错误码的含义以《系统接口与服务契约》为准，不在这里另列一套码值。

### 6.2 重试次数与退避

已确认：同一个任务的业务执行最多 4 次。只有 Go 可以分配 `attempt_no`，并且下一次只由用户调用手动重试触发。达到上限后任务保持 `FAILED`，`retry_allowed` 为否，再次手动重试返回 `ATTEMPT_LIMIT_REACHED`。用户仍可在终态后重新分析。前端不能改写次数后继续执行。

基础设施层可以做自己的有限恢复，但恢复成功只是同一次业务执行被重新接手，不是新的 `attempt_no`：

- Kafka 重复投递按 `event_id` 去重。
- Celery 在 Worker 崩溃后的恢复沿用原来的 `task_id`、`attempt_no` 和 `event_id`。
- 模型客户端的超时重试只发生在当前尝试内部。
- LangGraph 的有限纠错只发生在当前尝试内部。
- 恢复扫描在“仍在正常执行”和“正在恢复”时不调用失败事务，也不分配编号。

这些层不能各自再乘上新的业务执行。MVP 基线：模型单次请求超时 30 秒；单个节点最多一次结构修正；任务总执行期限 180 秒；发布/排队等待期限 120 秒；恢复判定窗口 60 秒。基础设施重投采用约 1、2、4 秒的指数退避并加随机抖动，最多 3 次。对支持 `Retry-After` 的限流响应，在当前尝试的总预算内遵守等待建议。所有参数均配置化。

### 6.3 继续对话、手动重试与重新分析

| 行为 | `thread_id` | `task_id` | `attempt_no` | 历史结果 |
|---|---|---|---|---|
| 继续对话 | 不变 | 不变 | 不变 | 追加对话消息。当前报告不变。不创建任务 |
| 当前尝试的基础设施恢复 | 不变 | 不变 | 不变 | 不产生新的对话消息、任务或当前报告 |
| 执行超时或执行中断且无法恢复 | 不变 | 不变 | 不变 | 失败事务把当前尝试收口为 `FAILED`，并写入对应失败码 |
| 用户手动重试失败任务 | 不变 | 不变 | 由 Go 递增，并使用新的 `event_id` | 计入最多 4 次。不创建新任务 |
| 用户主动重新分析 | 不变，新任务加入原线程 | 仅源任务已终态时新建 | 新任务从 1 开始 | 旧任务、旧报告和对话历史保留。同一事务保存 `user_note` 与前序关联。新任务重新读取 Diff |
| 重复 Kafka 事件或 Celery 恢复 | 不变 | 不变 | 不变 | 不产生新的对话消息、任务或当前报告 |
| 重复或过期结果回调 | 不变 | 不变 | 不变 | Go 拒绝覆盖。已接受的报告或已收口的失败保持不变 |

手动重试必须同时满足：状态为 `FAILED`，失败码允许重试，没有未结束尝试，并且已分配的业务执行次数少于 4。`SUCCEEDED` 和 `PARTIAL_SUCCESS` 不能调用手动重试。两个手动重试并发时，后失败的一方返回 `TASK_STATE_CONFLICT`，不分配 `attempt_no`。

重新分析与手动重试是两个产品行为。重新分析不复用 `/retry` 的语义，也不把原任务从终态拉回 `QUEUED`。源任务处于 `PENDING`、`QUEUED` 或 `RUNNING` 时，重新分析被拒绝。三种终态都可以重新分析；其中只有失败码允许且次数未用尽的 `FAILED` 才能手动重试。`user_note` 可省略。分析时不得把全部历史对话当作已证实输入。

## 7. Kafka、Celery 与数据库的一致性边界

### 7.1 最小异步链路

```text
Go API
  │
  ├── PostgreSQL 事务：创建 thread、task 与 outbox_event
  │
  ▼
Outbox 发布器
  │
  ▼
Kafka：analysis.requested
  │
  ▼
Python Kafka 消费者
  │
  ▼
Celery + Redis
  │
  ▼
LangGraph 分析工作流
  │
  ▼
Go 内部结果回调
  │
  ▼
PostgreSQL：attempt + report + task 状态
```

首版只要求打通分析请求所需的最小真实链路，不要求实现完整事件平台。

### 7.2 一致性要求

1. Go 在同一数据库事务中创建任务和待发布事件。
2. Outbox 发布失败时可恢复，不丢失分析请求。
3. Kafka 允许至少一次投递，业务处理必须幂等。
4. Kafka 消费者必须避免“确认已消费但内部任务实际未可靠入队”的丢失窗口。
5. 分析用的 Celery 任务必须携带 `task_id`、`attempt_no`、`event_id` 和追踪标识。对话回复任务携带 `thread_id`、对话事件标识和被引用的 `task_id`，不携带 `attempt_no`。
6. 分析结果回调必须携带 `task_id`、`attempt_no`、`event_id`。Go 校验调用方身份、该尝试是否仍是当前尝试，以及任务是否处于允许接收该结果的状态。过期尝试和重复回调都要拒绝，不能覆盖新结果。
7. 只有通过上述校验的结果才能更新任务状态和当前有效报告。对话回复回调只追加 Agent 消息，不能修改任务状态或报告。
8. 数据库状态提交成功但回调响应丢失时，使用同一 `event_id` 的重复回调应返回已接受的结果，而不是再写一份报告。
9. HTTP 创建任务的幂等键只判断“相同用户、相同键、相同请求内容是否为同一次创建”。它与 Kafka 消费记录不是同一套数据。相同幂等键但请求内容不同，必须拒绝，不能返回另一个任务。
10. Python 消费 Kafka 后，先把任务可靠交给 Celery，再提交 Offset。投递失败不得提交 Offset。消费侧必须保留 `event_id` 处理记录或等价的原子去重。
11. 若进程在 Celery 已经接收任务之后、Offset 提交之前崩溃，Kafka 会再次投递。消费记录和 `event_id` 必须使这次重投回到原执行，而不是创建新任务或新的 `attempt_no`。
12. Outbox 长期未发布、任务长时间停留在 `QUEUED` 或 `RUNNING`、对话回复长期没有落库、消费积压，都必须能被发现。恢复时以 PostgreSQL 中的任务、尝试和 Outbox 记录为准重新发布或重新接手，不另建中间件。已发布但未完成的分析继续使用原来的 `attempt_no`。只有确认无法恢复时才把当前尝试收口为 `FAILED`，并且不分配下一个编号。
13. Kafka、Redis 或 Python 服务重启后，未完成的业务执行和未完成的对话回复都要根据持久化记录恢复，不能把线程上下文串到另一次执行。

### 7.3 暂不要求的复杂机制

首版不默认引入分布式事务、复杂 Saga 编排、多集群 Kafka 或通用事件平台。

但不能因此省略事务 Outbox、消费幂等、重试上限、失败诊断和恢复验证。这些是当前选定架构成立的必要条件。

## 8. 数据保留与隐私

### 8.1 已确认要求

- Diff 存储在 PostgreSQL。
- 原始代码有大小限制和保留规则。
- 用户提交前必须知晓 Diff 会发送给外部模型，完成确认，并且系统留存确认记录或审计事件。
- 原始 Diff、密钥、Token 和完整对话正文不写入普通日志。
- 线程、对话消息、任务、报告和输入都必须属于明确的用户。用户只能访问自己的这些数据。

### 8.2 保留与删除的实施基线

以下默认值与规则已在《认证权限与安全设计》中确定，实施时须落实清理逻辑：

- Diff 最大 1 MiB；最多 500 个变更文件；新增与删除行数合计最多 20,000 行；解析时限 5 秒。
- 原始 Diff 保留 30 天；报告、证据、任务元数据和对话保留 90 天；审计日志保留 180 天。
- 用户自助删除 UI 不属于 MVP，但必须提供可执行的账号删除运维流程。
- 清理作业须分批、可重入、可审计；备份中的过期数据删除延迟在部署说明中披露。
- 模型 API Key 由服务端环境变量或部署密钥设施注入，不能写入仓库或日志。
- MVP 不强制实现完整 DLP；如检测到疑似密钥，可拒绝提交并提示用户脱敏，不能自动把疑似密钥转发给模型。

## 9. 数据库约束与索引原则

最终迁移脚本至少需要覆盖以下约束类别：

1. 用户邮箱唯一性。
2. 任务到用户的外键关系。
3. 输入到任务的关联约束。
4. 同一任务的尝试序号唯一性。
5. 报告到任务和尝试的来源关联。
6. 事件 ID 唯一性及消费端幂等约束。
7. 任务状态合法值与合法迁移校验。
8. 必要的非空约束、时间字段一致性约束。
9. 按用户查询任务、按任务查询尝试和报告的索引。
10. Outbox 待发布事件、消费记录和过期数据清理所需的索引。

具体索引应根据实际查询模式确定，不应为了“企业级”而给所有字段增加索引。外键删除策略也不能直接统一使用级联删除，因为审计记录、失败诊断和报告保留可能存在不同要求。

## 10. 数据库与任务状态验收要求

在进入业务代码实现之前，至少明确以下测试。

### 10.1 任务生命周期

- 正常任务能从创建走到完整成功。
- 核心风险分析成功、非核心分析失败时，正确产生部分成功报告。
- 核心风险分析失败时，不产生伪装成完整成功的报告。
- 不合法状态迁移会被拒绝。
- 终态任务不会被重复消息重新启动。

### 10.2 重试与幂等

- 手动重试使同一任务的业务执行不超过 4 次。失败回调、超时收口和恢复扫描不增加 `attempt_no`。
- 不可手动重试的错误接受失败记录，但不接受手动重试。
- `SUCCEEDED` 和 `PARTIAL_SUCCESS` 不能通过手动重试重新执行。
- 同一个 `event_id` 重复消费不会产生新的 `attempt_no` 或新任务。
- 旧尝试回调不会覆盖新尝试结果，也不会覆盖已接受的报告或已收口的失败。
- 重复结果回调不会重复创建当前有效报告。
- 次数用尽后可以查询最终失败原因和历史尝试，`retry_allowed` 为否，再次手动重试被稳定拒绝。
- 仍在执行期限内的尝试不会被扫描器收口。确认超时或中断后，失败码分别为 `EXECUTION_TIMEOUT` 和 `EXECUTION_INTERRUPTED`。
- 继续对话不改变尝试次数；重新分析只在新任务上从 1 开始计数，并保存可选 `user_note` 与前序关联。
- 并发手动重试只有一方分配新的 `attempt_no`。

### 10.3 消息可靠性

- 创建任务的数据库事务回滚时，不会留下可被正常发布的孤立事件。
- Outbox 发布过程中服务崩溃后，事件可以恢复发布。
- Kafka 重复投递时，消费者能够幂等处理。
- 内部任务入队后、Kafka offset 提交前发生故障时，不会丢失任务。
- Go 回调失败或超时后，可以通过安全重试完成状态更新。

### 10.4 数据隔离与隐私

- 用户 A 无法读取用户 B 的线程、对话消息、任务、Diff、报告或执行记录。
- 非法任务 ID、越权手动重试、越权重新分析和伪造内部回调均被拒绝。
- 日志中不出现原始 Diff、完整对话正文、模型密钥或认证 Token。
- 缺少已留存的外部模型确认时，不能创建会把 Diff 送往模型的任务。
- Diff 超出大小上限时，在进入昂贵分析流程前被拒绝。
- 过期数据清理可以重复执行且不会破坏仍需保留的数据。

### 10.5 性能与恢复

- 记录 PostgreSQL 关键查询的耗时和执行计划。
- 监测连接池占用、慢查询、Outbox 积压、Kafka 消费延迟和 Celery 队列积压。
- 测试 Worker 重启、Kafka 暂停、Redis 重启、模型接口超时等故障场景。
- 建立首轮端到端基线；后续优化在相同样本、相同负载和相同环境下复测。

性能目标和测试负载暂不在本文档冻结，由《测试与性能验证方案》统一定义。

## 13. MVP 物理实现默认值

为避免实现阶段重复决策，首版采用以下物理实现默认值：

- 主键统一使用 UUID；时间统一使用带时区的 `TIMESTAMPTZ`，应用和数据库以 UTC 存储。
- 结构化报告、节点输出、检测到的语言和事件载荷使用 `JSONB`；正文、Diff、受控诊断摘要使用 `TEXT`。
- `threads`、`conversation_messages`、`task_inputs`、`report_evidence`、`consumed_events`、`knowledge_documents`、`knowledge_chunks`、`agent_memories` 均采用独立表；消费去重表对 `event_id` 建唯一约束。
- `knowledge_chunks` 使用 PostgreSQL `pgvector` 扩展保存 BGE-M3 生成的向量；向量维度、距离度量和索引类型按选定模型与评测结果冻结，不在未测试前虚构最优参数。
- `agent_memories` 必须包含 `user_id` 与来源/状态信息；所有查询强制用户隔离。
- `tasks.current_attempt` 与 `task_attempts.attempt_no` 由同一事务维护；`attempt_no` 对 `(task_id, attempt_no)` 建唯一约束。每个任务最多 4 次业务执行。
- `task_inputs.source_type` 为 `TEXT` 或 `FILE`；用户状态为 `ACTIVE` 或 `DISABLED`；消息角色为 `USER`、`ASSISTANT` 或 `SYSTEM`。
- 默认期限：模型单次请求 30 秒，发布/排队等待 120 秒，任务执行 180 秒，恢复判定 60 秒；基础设施自动重投最多 3 次，退避约 1、2、4 秒并加随机抖动。
- 默认保留期按《认证权限与安全设计》执行：Diff 30 天、报告/证据/任务元数据与对话 90 天、审计日志 180 天。Outbox/消费去重记录按恢复和幂等需求单独清理。

以上为 MVP 工程基线，不是性能承诺。参数可以在测试后调整，但必须更新配置说明、测试和本文件。
