# CodeRisk 产品需求与业务规则（PRD）

**文档版本：** V1.1（修订稿）  
**文档状态：** 待审查；需求设计阶段，尚未编码实现  
**所属项目：** CodeRisk——代码变更风险评估与任务难度量化平台  
**文档用途：** 定义产品范围、用户流程、业务规则与验收要求；不替代架构、数据库、接口、Agent、安全等专项设计。

---

## 1. 产品概述

### 1.1 产品定位

CodeRisk 是一个面向 Java、Python 代码变更的风险评估与任务难度量化 Web 平台。

用户提交 Diff 文本或 Diff 文件后，系统提取可确认的代码事实，结合相关知识检索与 Agent 分析，生成结构化评估计划书。计划书帮助用户理解本次变更的风险、难度、证据、影响判断、测试重点和后续核查建议。

产品的核心问题是：

1. 这次变更有哪些值得关注的风险？
2. 任务难在哪里，哪些因素影响实现与验证成本？
3. 哪些内容有代码证据支持，哪些只是推断或待验证假设？
4. 应优先检查和测试什么？

CodeRisk 是辅助评估与决策工具，不替代开发者、代码审查人员或测试人员作最终判断。

### 1.2 目标用户

首版面向个人使用者，包括开发人员、代码审查人员和技术负责人。每个账号独立使用系统，不建设复杂的组织、团队协作或企业审批体系。

### 1.3 产品边界

**首版支持：**
- 邮箱注册、登录与个人数据隔离。
- 提交 Diff 文本或 Diff 文件。
- 对 Java、Python 变更进行事实提取与分析。
- 生成包含 Risk、Hardness、证据、测试建议和分析限制的评估计划书。
- 查看任务状态、历史任务、历史报告与同一线程的对话。
- 基于已有报告追问、质疑结论。
- 对符合条件的失败任务手动重试。
- 创建新的重新分析任务，并保留旧任务和旧报告。
- 通过 RAG、Embedding、向量检索和 Agent Memory 提供有边界、可追溯的相关上下文能力；具体数据范围、写入规则、隔离、删除和评测标准由《Agent 工作流与证据规范》定义。

**首版不支持：**
- 读取用户本地仓库、自动克隆仓库或接入 Commit/PR。
- 自动修改、生成补丁、应用补丁、执行用户代码、构建脚本或测试脚本。
- 自动提交、推送或合并代码。
- 用户主动取消已提交任务（首版不提供取消能力）。
- 完整团队、组织、协作权限和企业级审批。
- 把模型推断表述为已经证实的代码事实。

由于输入只有 Diff 和系统明确获取的上下文，系统不得声称已经掌握完整仓库依赖图、全部调用链或完整影响范围。报告必须区分直接观察到的事实、基于事实的推断，以及仍需补充信息或人工核验的假设。

### 1.4 产品假设

风险识别、审查提效、测试建议和难度评估的业务价值仍需通过固定评测集与真实案例验证。当前没有可用于宣称生产准确率、实际节省工时或线上用户收益的数据。

## 2. 产品目标与成功标准

### 2.1 首版目标

1. 用户可以安全地注册、登录并独立使用系统。
2. 用户能够提交支持范围内的 Diff 并查看任务进度。
3. 系统能够生成结构化、带证据和限制说明的评估计划书。
4. 用户可以查看历史任务与报告，并针对报告追问或质疑。
5. 重试、重新分析、失败收口和历史保留符合统一业务规则。
6. RAG、向量检索和 Agent Memory 在限定范围内工作，能够追溯检索来源、记忆来源及其对结论的影响。
7. 系统具备可重复执行的功能、安全、Agent 质量、性能和可靠性测试。
8. 提供可复现的容器化演示部署方式。

### 2.2 成功标准

验收至少关注：
- 核心业务流程可完整运行。
- 风险结论和关键建议能关联到真实证据或明确标注为推断。
- RAG 检索内容具有来源、相关性与访问边界；记忆读写符合数据隔离和用户可控规则。
- 异步任务、重试、幂等、恢复和报告生效规则通过测试。
- 可测量端到端耗时、吞吐量、P50/P95、错误率、队列积压、资源使用与模型调用成本。
- 优化前后使用可比较的环境、数据集和参数复测。

不在缺乏测试基线时预设或宣称准确率、性能容量与优化比例。

## 3. 核心业务概念

### 3.1 Risk：变更风险

Risk 表示本次变更可能引入的问题及其潜在影响程度。关注逻辑缺陷、边界条件、接口兼容性、数据一致性、权限与安全边界、异常处理、关联模块影响及测试缺口等。

风险等级固定为：
`CRITICAL`、`HIGH`、`MEDIUM`、`LOW`、`INFO`。

风险等级用于辅助确定审查优先级，不代表缺陷必然发生的概率，也不证明代码必然存在真实 Bug。首版不输出未经校准的缺陷概率分数。

每项重要风险应尽可能包含：
- 标题、描述与风险等级。
- 对应代码位置或其他可核查证据。
- 可能影响及其推理依据。
- 建议验证方式。
- 证据充分程度或不确定性说明。

### 3.2 Hardness：任务难度

Hardness 表示完成这项变更所需的技术理解、实现和验证工作的相对难度，不等同于 Risk、代码行数或精确工时预测。

难度因素包括模块与依赖范围、业务逻辑复杂度、接口或数据模型变化、并发与状态处理、异常分支、测试成本，以及对领域知识和跨模块上下文的依赖程度。

等级固定为 `LOW`、`MEDIUM`、`HIGH`、`VERY_HIGH`。首版不把等级包装成精确工时；若输出 `score`，其默认值为 `null`，具体结构由 Agent 契约定义。

### 3.3 事实、判断与假设

报告必须区分：

1. **确定性事实：** 可直接从输入 Diff、解析结果或明确来源中核验的信息。
2. **分析判断：** 基于事实推导出的风险、影响或难度。
3. **待验证假设：** 需要完整仓库上下文、测试运行、业务方说明或人工核验才能确认的内容。

不得虚构文件路径、代码行、函数、依赖关系、检索来源或工具结果。证据不足时应明确说明限制，而不是为了填满报告强行下结论。

## 4. 用户流程与任务规则

### 4.1 主流程

1. 用户注册或登录。
2. 在提交前看到明确提示：Diff 及分析所需内容将发送到系统配置的外部模型服务；用户确认后才能提交分析。系统留存确认记录。
3. 用户提交 Diff 文本或 Diff 文件。
4. 系统创建任务，立即返回任务标识，后台执行分析。
5. 用户查看任务状态；任务结束后查看评估计划书。
6. 用户可以针对当前报告追问或质疑，也可以在终态后发起重新分析。
7. 仅符合条件的 `FAILED` 任务允许手动重试。

继续对话、手动重试、重新分析是三种不同操作，不能混为一谈。

### 4.2 用户可见任务状态

| 状态 | 含义 |
|---|---|
| `PENDING` | 任务已接受，等待进入分析队列 |
| `QUEUED` | 已进入队列，等待执行 |
| `RUNNING` | 当前业务执行正在分析 |
| `SUCCEEDED` | 核心分析及规定的必要产物完成，报告可用 |
| `PARTIAL_SUCCESS` | 核心风险分析已完成，但部分非核心分析未完成；属于终态 |
| `FAILED` | 未形成可用的核心风险分析结果；属于终态 |

不向用户展示独立的 `CANCELLED`、`RETRY_WAIT` 或“正在恢复”状态。基础设施恢复、Kafka 重投或 Celery 恢复属于当前业务执行的内部过程，不创建新的业务尝试。

当前尝试经恢复判断确认无法继续时，任务进入 `FAILED`。执行期限、恢复判定窗口和错误码的具体参数由任务状态与接口专项文档统一定义，PRD 不再维护另一套实现细节。超时或中断不得自动启动下一次业务执行；仍可恢复的任务保持未结束状态。

`PARTIAL_SUCCESS` 必须明确列出未完成的分析项及其影响，不自动补跑。失败任务必须有可识别的失败原因，不得被显示成成功，也不得无限期停在无法判断是否仍在运行的状态。前端只依据接口返回的 `retry_allowed` 决定是否显示重试入口。

### 4.3 报告与后续对话

每个分析任务最多只有一份当前有效报告。历史任务及其报告应持续可查看，不得由后续分析静默覆盖。

用户可以针对已有报告追问原因、证据、影响和测试建议。系统在接受消息时绑定其讨论的任务与报告；用户可以指定同一线程中的历史报告。回复只能以绑定的报告及其可用证据为上下文，不能把其他任务的结论自动当作当前事实，也不能修改原报告。

普通追问不创建分析任务、不增加业务执行次数，也不改变任务状态。追问失败不影响报告。若用户希望重新计算分析结论，必须明确发起重新分析。

在任务尚未形成有效报告时，用户仍可以查看对话历史和失败说明，但系统不能伪造一份新的分析报告。

### 4.4 三种操作的区别

| 操作 | 业务行为 | 历史保留 |
|---|---|---|
| 继续对话 | 追加消息和回复，不创建新任务、不增加业务执行次数 | 保留全部对话记录 |
| 手动重试 | 仅对 `retry_allowed=true` 的 `FAILED` 任务执行；Go 为新业务尝试分配 `attempt_no` | 原任务和失败记录保留；成功后更新该任务的当前有效报告 |
| 重新分析 | 在同一对话线程中创建新任务，重新分析原 Diff；允许附带可选 `user_note` | 旧任务和旧报告保留，新结果属于新任务 |

任务最多允许 4 次业务执行。`SUCCEEDED` 和 `PARTIAL_SUCCESS` 不允许手动重试。达到次数上限、失败类型不允许重试或当前仍有未结束执行时，重试请求必须被拒绝并返回明确原因。重新分析只能在任务进入终态后发起。

Kafka 重投、Celery 恢复、模型内部重试、LangGraph 内部纠错和恢复扫描均不得增加业务执行次数或创建新任务。普通追问即使包含“重新分析”等文字，也不能自动触发任务创建。

### 4.5 重新分析与原始输入保留

重新分析创建新任务并重新提取事实与证据。可选 `user_note` 是用户提供的补充说明，不修改原始 Diff，也不自动把全部历史消息注入新任务。

重新分析必须读取原任务对应的不可变 Diff 副本。如果原始 Diff 已根据保留策略清理，接口返回 `SOURCE_INPUT_EXPIRED`，用户需要重新提交 Diff。历史报告仍可查看。

### 4.6 不支持取消

用户不能取消已经提交的任务。首版不提供取消接口或取消状态。不能通过前端关闭页面来宣称后台任务已取消。

## 5. 输入与分析范围

### 5.1 输入形式

首版只接受：
- Diff 文本。
- Diff 文件。

两种输入统一规范化为一个任务的一份不可变 Diff。仓库、Commit、PR、压缩包或本地路径不是首版输入，不能在页面上保留为可选入口。

当前 PRD 的默认输入限制为：Diff 不超过 1 MiB、最多 500 个变更文件、增删行合计不超过 20,000 行；解析时限默认 5 秒。以上均为待测试校准的服务端配置，具体校验行为和错误码以接口契约为准。

### 5.2 语言范围

首版重点支持 Java 与 Python。对于不支持的语言、无法解析的语法、超限输入或不完整 Diff，系统必须返回明确反馈，并在报告或任务结果中说明分析覆盖限制。

### 5.3 分析可使用的上下文

系统可以使用：
- 本次 Diff 及其确定性解析结果。
- 在当前输入范围内可验证的代码结构信息。
- 明确配置并可访问的项目知识或通用技术知识。
- RAG/Embedding/向量检索返回的相关材料。
- 经授权、符合隔离与保留规则的 Agent Memory。
- 当前任务中可追溯的分析中间结果与工具结果。

所有检索结果和记忆都必须标记来源与适用范围。检索到的信息不能自动升级为代码事实；跨用户数据不能混用。Agent Memory 的读写、过期、纠错、用户隔离和删除规则必须在 Agent 专项文档中明确，并纳入测试。

首版不执行用户任意代码、构建脚本或测试脚本。解析器和静态分析工具需要设置资源限制；具体实现及隔离边界由架构与安全文档规定。

## 6. 评估计划书需求

### 6.1 必须包含的内容

| 部分 | 说明 |
|---|---|
| 任务概要 | 输入摘要、分析状态、覆盖范围 |
| 变更概览 | 变更文件、主要增删改内容 |
| 风险总览 | 主要风险、等级与审查优先级 |
| 风险详情 | 风险描述、证据、推理依据、潜在影响和验证方式 |
| Hardness 评估 | 难度等级、主要影响因素及依据 |
| 测试建议 | 建议优先验证的场景、边界条件和关联模块 |
| 知识与上下文来源 | 对结论有实质影响的检索材料或记忆来源，按专项契约展示 |
| 分析限制 | 缺失上下文、解析失败、检索不足、不确定结论和未完成项目 |

### 6.2 证据与追溯

重要风险应尽可能回答：风险在哪里、为何值得关注、哪些事实支持判断、可能造成什么影响、如何验证。

代码位置必须来自真实输入或可验证的解析结果。引用知识材料或记忆时，应能定位到实际来源；无法定位的内容不得伪装成有出处的事实。

### 6.3 报告元数据与版本

报告必须关联任务、生成报告的业务执行、输入 Diff 版本和相关证据。必要诊断元数据包括模型供应商/模型标识、提示词或工作流版本、关键阶段耗时与错误码。不得保存模型密钥、完整认证令牌或不必要的原始敏感内容。

重新分析产生新任务与新报告；旧报告正文不可被新结论覆盖。报告结构、字段类型和持久化字段由 Agent 契约与数据库设计定义。

## 7. MVP 功能范围

### 7.1 首版必须实现

| 模块 | 最低要求 |
|---|---|
| 账号与认证 | 邮箱注册、登录、Access Token 与 Refresh Token 生命周期管理；细节由认证安全文档定义 |
| 用户数据隔离 | 线程、消息、任务、Diff、报告、记忆及相关检索数据按用户边界访问 |
| 外部模型确认 | 提交前告知外部模型处理并取得确认，保存确认记录 |
| Diff 输入 | 支持文本与文件，具备大小、行数、文件数和解析时间限制 |
| 任务管理 | 创建、状态查询、历史查看、符合条件的手动重试、重新分析 |
| 对话 | 追问与质疑不创建任务、不改变报告 |
| 代码事实提取 | 提取变更事实，明确处理解析失败 |
| Agent 分析 | 使用有明确职责、结构化输入输出和证据要求的工作流 |
| RAG 与向量检索 | 支持受控知识材料的索引、检索、来源追溯和质量评测 |
| Agent Memory | 支持限定范围、可追溯、隔离且可治理的记忆读写；不得跨用户泄露或无条件累积 |
| 风险评估 | 输出 Risk、等级、证据和影响说明 |
| 难度评估 | 输出 Hardness、因素和判断依据 |
| 测试建议 | 输出与变更相关的验证建议 |
| 报告管理 | 保存当前报告与历史报告，禁止静默覆盖 |
| 异步处理 | 明确任务状态、幂等、重试和失败收口 |
| 可观测性 | 结构化日志、关联 ID、关键耗时、错误率与队列指标；避免记录原始 Diff 和秘密 |
| 自动化测试 | 覆盖功能、权限、Agent 质量、RAG/Memory、安全、性能与可靠性 |
| 部署 | 提供可复现的容器化部署与演示方式 |

Kafka 是项目确定的技术方向，需纳入跨服务事件链路设计。Go/PostgreSQL 负责业务任务与报告的权威状态；Python Agent 不直接写业务数据库。Kafka、Outbox、消费去重以及 Redis/Celery 的职责边界由总体架构、数据库和接口文档统一定义。

### 7.2 首版不包含

- 仓库、Commit、PR 接入。
- 用户取消任务。
- 对 `SUCCEEDED` 或 `PARTIAL_SUCCESS` 任务手动重试。
- 自动补跑部分成功任务中失败的非核心分析。
- 自动修改、生成或应用代码补丁。
- 执行用户代码、构建脚本或测试脚本。
- 自动提交、推送或合并代码。
- 完整团队、组织和企业级审批体系。
- 多 Agent 无业务边界的自由讨论或无限循环。
- 无数据隔离、来源追溯和治理规则的全局记忆。
- 未经评估就接入与业务无关的中间件或工具协议。
- 没有测试证据支撑的准确率、性能或可靠性承诺。

### 7.3 范围变更原则

任何新增或删减能力都必须记录：
1. 要解决的业务问题；
2. 是否已有需求或测试证据；
3. 对架构、数据模型、安全和运维的影响；
4. 实现与维护成本；
5. 是否需要同步修改验收标准及相关文档。

RAG、Embedding、向量检索和 Agent Memory 已列入当前设计范围，不能在其他专项文档中被静默删除或降为“可选项”。具体技术选型、数据范围和首版最小实现需在架构与 Agent 专项文档中统一定义；不得仅为技术展示增加无业务价值的复杂度。

## 8. 验收标准

### 8.1 功能验收

- 用户可注册、登录，并在页面刷新后恢复合法会话。
- 未确认外部模型处理前不能提交分析。
- 用户可提交 Diff 文本或文件，创建任务并查询状态。
- 有效输入能够走完分析流程并生成计划书。
- 报告包含 Risk、Hardness、证据、测试建议和分析限制。
- 用户可追问或质疑，且不会因此创建任务、改变报告或增加业务执行次数。
- `retry_allowed=true` 的失败任务可手动重试；成功、部分成功、次数用尽或不符合重试条件的任务不能重试。
- 超时或中断且确认无法恢复时进入 `FAILED`，返回可区分错误码，不自动启动下一次业务执行。
- 重新分析创建新任务；旧任务和报告保留；未结束任务不能重新分析。
- 原始 Diff 到期后，历史报告仍可查看，但重新分析返回 `SOURCE_INPUT_EXPIRED`。
- 部分成功明确说明缺失的非核心分析，不自动补跑。
- 非法、超限或不可解析输入得到明确反馈。
- 用户不能通过更改请求参数读取其他用户的线程、消息、任务、Diff、报告、记忆或检索数据。
- RAG 结果可追溯到实际来源；Agent Memory 的读写遵守用户隔离、范围和删除规则。
- 任务状态、业务执行记录和报告保持一致；页面重新加载后关键记录仍可查询。

### 8.2 Agent 与分析质量验收

建立固定代码变更评测集，覆盖典型风险、正常变更、复杂任务、边界条件、证据不足及不应误报场景。每个案例需要可检查的参考答案或评判规则。

至少记录：
- 风险识别的准确性、召回情况和误报情况。
- 代码证据是否真实、位置是否正确。
- 风险解释是否与证据一致。
- Hardness 判断是否符合预先定义的规则。
- 测试建议是否覆盖关键场景。
- RAG 检索相关性、来源准确性及无关内容干扰情况。
- Memory 读取是否命中适当内容、是否出现错误写入或跨用户泄露。
- 多次运行的稳定性，以及模型服务失败时的行为。

不能仅依赖模型自我评分作为最终质量证明；必要时结合人工标注、确定性校验和对照实验。

### 8.3 系统性能验收

分别开展组件测试与完整业务链路测试。至少记录：
- 并发请求数、成功率、吞吐量、P50/P95 延迟。
- 分析任务端到端耗时、排队等待时间和队列积压。
- PostgreSQL 连接池、查询耗时和资源使用。
- Kafka 生产/消费延迟、重复消息和积压。
- Redis/Celery 任务执行与恢复情况。
- RAG 检索耗时、向量检索质量和资源占用。
- 模型调用耗时、失败率与成本。
- CPU、内存和整体错误率。

目标值须在测试环境、输入规模、模型服务和资源配置明确后制定，不得脱离测试条件宣称容量。

### 8.4 安全与可靠性验收

至少覆盖：
- HTTP 幂等：同一幂等键、相同内容返回原结果；相同键、不同内容拒绝。
- Outbox 与事件投递的一致性。
- Kafka 重投、重复消费、Celery 恢复与服务重启不新增业务执行。
- 单任务业务执行最多 4 次；并发手动重试仅一方成功。
- 过期或重复回调不能覆盖当前报告。
- 用户数据越权访问与记忆/检索数据隔离。
- Diff 超限、异常解析内容、临时文件清理与资源限制。
- 外部模型超时、限流和不可用。
- 未确认外部模型处理时不能提交任务。
- 日志与错误响应中不泄露原始 Diff、密码、令牌、模型密钥或其他秘密。

首版不要求完整生产级容灾，但不能忽略影响基本可用性和数据安全的关键风险。

## 9. 测试与优化闭环

项目执行两轮完整测试，不预设必然达到某个优化比例。

### 第一轮：MVP 基线测试

1. 业务功能与权限测试。
2. 固定 Agent 评测集。
3. RAG 检索质量与来源追溯测试。
4. Agent Memory 读写、隔离、删除和误用测试。
5. API 并发与端到端压测。
6. PostgreSQL、Kafka、Redis/Celery 相关测试。
7. 幂等、重复消费、失败恢复与回调测试。
8. 资源消耗、延迟、错误率和模型调用成本测试。

### 第二轮：优化后复测

针对第一轮中证据明确的问题优化，再使用尽可能一致的环境、数据集与测试参数复测。对比指标变化、优化措施、是否引入新问题以及结果是否可重复。若改善不明显，应如实记录。

简历中的所有量化结果必须能追溯到真实测试记录，不得把本地压测描述成生产线上数据。

## 10. 跨文档职责与待专项定义项

本 PRD 负责产品范围与业务规则，不重复维护技术实现细节。以下内容由对应专项文档统一定义：

| 专项文档 | 必须明确的内容 |
|---|---|
| 总体架构与技术决策 | 服务职责、Go/Python 边界、Kafka/Outbox、Redis/Celery、部署拓扑、模型适配 |
| Agent 工作流与证据规范 | Agent 节点职责、结构化输出、证据门禁、RAG 检索链路、Memory 数据范围与治理、部分成功判定 |
| 数据库与任务状态设计 | 表结构、状态迁移、attempt_no、报告生效、Outbox、幂等记录、保留与清理 |
| 系统接口与服务契约 | API、请求/响应、错误码、回调、`retry_allowed`、幂等键语义 |
| 认证权限与安全设计 | Access/Refresh Token、邮箱注册规则、密码与令牌保护、外部模型确认、数据隔离、日志脱敏 |
| 开发实施与验收计划 | 分阶段实现、测试顺序、基线与优化复测、部署和验收证据 |

本 PRD 当前明确：Access Token 与 Refresh Token 均属于认证需求；RAG、Embedding、向量检索和 Agent Memory 属于设计范围；用户不能取消已提交任务；首版不执行或修改用户代码。向量检索的默认设计方案为 PostgreSQL + pgvector，首选 Embedding 模型为 BGE-M3；其检索质量、延迟、资源占用、维度兼容性与用户数据隔离仍须通过测试验证，不能视为已验证的最优选型。令牌传输方式、刷新与撤销策略、记忆分类与生命周期、任务期限参数等，应在专项文档中形成唯一一致的决策，不得由不同模块各自假设。
