# CodeRisk 设计决策与变更记录

**文档版本：** V1.1 修订稿
**文档状态：** 待交叉审查；本文记录当前设计方向，不代表代码已实现或验收测试已通过。
**项目名称：** CodeRisk——代码变更风险评估与任务难度量化平台

## 一、关键决策

| 主题 | 最终决策 | 主要依据文档 |
|---|---|---|
| 产品输入 | Web 端只接受 Diff 文本或 Diff 文件；不接收仓库、Commit、PR；Diff 仅用于静态分析，不执行代码 | 项目总纲、PRD、接口契约 |
| 支持范围 | 正式支持 Java 内部变更和 Python 内部变更，包括缺陷修复、功能修改、重构；跨语言迁移不是 MVP 正式场景 | PRD、总体架构、Agent 规范 |
| 业务权威 | Go + PostgreSQL 负责身份、任务、尝试、报告、对话与审计；Python 只分析并回调 | 总体架构、接口契约、数据库设计 |
| 异步链路 | PostgreSQL 事务 Outbox → Kafka → Python 消费者 → Celery/Redis → LangGraph → 鉴权回调 Go | 总体架构、接口契约、开发实施计划 |
| 任务状态 | `PENDING`、`QUEUED`、`RUNNING`、`SUCCEEDED`、`PARTIAL_SUCCESS`、`FAILED`；不提供取消 | PRD、数据库设计、接口契约 |
| 业务执行次数 | 每任务最多 4 次；Go 只在初始执行和合规手动重试时分配 `attempt_no` | 数据库设计、接口契约 |
| 重试/恢复 | 基础设施恢复、Kafka 重投、Celery 恢复和模型内部纠错不新增业务尝试；仅合规手动重试新增尝试 | 总体架构、数据库设计、接口契约 |
| 超时默认值 | 发布/排队 120 秒；执行 180 秒；恢复窗口 60 秒；模型单次调用 30 秒 | PRD、总体架构、数据库设计、接口契约 |
| 基础设施重投 | 最多 3 次，约 1/2/4 秒指数退避并加随机抖动；不得扩增业务执行次数 | 总体架构、数据库设计、接口契约 |
| Diff 默认限额 | 1 MiB；500 个变更文件；增删行合计 20,000 行；解析 5 秒 | 安全设计、PRD、接口契约 |
| 数据保留 | Diff 30 天；报告/证据/任务元数据/对话 90 天；审计日志 180 天 | 安全设计、数据库设计 |
| 风险与难度 | Risk：`CRITICAL/HIGH/MEDIUM/LOW/INFO`；Hardness：`LOW/MEDIUM/HIGH/VERY_HIGH`；不伪造精确概率或工时 | Agent 规范、PRD |
| 核心成功标准 | 核心风险结果必须结构有效且证据可核验；核心失败为 `FAILED`；非核心节点缺失才可能 `PARTIAL_SUCCESS` | Agent 规范、PRD、接口契约 |
| Agent 形态 | Python FastAPI + LangGraph；节点按分析职责组织，不因多 Agent 而拆成多个微服务；不引入 MCP | Agent 规范、总体架构 |
| RAG 与 Embedding | 属于当前设计范围；BGE-M3 负责向量编码，PostgreSQL + pgvector 作为首选向量存储与检索方案，暂不默认采用独立 Milvus | Agent 规范、总体架构、数据库设计 |
| Agent Memory | 属于当前设计范围；仅使用有明确来源、状态和用户归属的记忆；按用户隔离，不把所有历史对话自动拼入上下文 | Agent 规范、数据库设计、安全设计 |
| 模型密钥 | 服务端持有模型 API Key；不支持用户自带 Key；前端不接触密钥 | 安全设计、总体架构 |
| 代码安全 | 不执行用户 Diff 中的代码、脚本或命令；不开放任意 Shell/URL/内网探测 | 安全设计、Agent 规范 |
| 用户隔离 | 所有任务、报告、输入、线程、消息及 Agent Memory 按认证用户授权；Python 不直接写业务数据库 | 安全设计、数据库设计 |
| 模型数据外发 | 提交前明确告知 Diff 和必要上下文会发送到平台配置的外部模型供应商，并记录用户确认；日志不得记录原始 Diff、密钥或完整提示词 | PRD、安全设计、接口契约 |
| 认证 | 邮箱注册/登录；Access Token + Refresh Token；不支持用户自带模型 Key | PRD、安全设计 |

## 二、明确不属于 MVP 的内容

- 仓库/Commit/PR 集成、代码执行或自动运行测试。
- 独立 Milvus 部署、MCP 工具平台、全仓调用图、完整 AST 服务；RAG、Embedding 和有边界的 Agent Memory 不在排除范围内。
- 组织/团队多租户、SSO、MFA、第三方登录、用户自带 API Key。
- 用户取消任务、自动创建新的业务执行尝试、无边界的跨任务长期记忆。
- 未经真实测试支持的准确率、P95、成本节省或业务收益承诺。

## 三、待验证假设与实施阶段任务

以下方向已作为当前设计基线，但具体效果必须通过实现和测试验证，不应提前宣称最优或达标：

- BGE-M3 在当前知识语料上的检索质量、向量维度与资源开销。
- PostgreSQL/pgvector 在目标数据规模下的检索延迟、索引策略和并发表现。
- Agent Memory 的实际收益、写入门槛、过期/删除规则及跨用户隔离测试。
- 模型输出的风险命中率、误报率、证据有效率、Hardness 一致性、端到端延迟与调用成本。
- Kafka、Celery/Redis、PostgreSQL 在重复投递、进程中断、恢复和并发重试下的可靠性。

以下属于实施工作，不应被误读为设计已经实现：

1. 按开发实施计划先检查实际仓库、Git 状态、环境和现有实现。
2. 将文档契约落成数据库迁移、OpenAPI/接口定义、Kafka 事件 schema 与 Python Pydantic 模型。
3. 对默认限额、超时、恢复窗口、重投退避和数据清理做故障测试；根据测试数据调参并更新文档。
4. 先在固定评测集和可记录的环境中运行 MVP 基线，再针对真实问题优化，最后用相同评测集和可比条件进行完整复测。
5. 同时记录功能正确性、证据有效率、风险命中/误报、Hardness 一致性、P50/P95、吞吐量、错误率、队列等待、数据库/Kafka/Celery 指标、资源占用和模型成本。
6. 为请求、任务、尝试、事件和模型调用建立关联标识；日志不记录原始 Diff、密钥或不必要的敏感正文。
7. 只有真实测试完成后，才报告通过率、性能或成本指标。

## 四、版本和偏差管理

如实现与本文档不同，必须在同一个变更中说明：偏差原因、影响文档、迁移兼容性、测试证据和回滚方案。不能由前端、Go 或 Python 各自决定状态、枚举、重试或报告语义。


## 五、文档状态与同步规则

1. 本文的“当前决策”是文档设计基线，不等于已经在代码中实现。所有性能、质量和可靠性结论均须等待测试证据。
2. 当产品范围或关键业务规则变化时，先更新《产品需求与业务规则》，再识别受影响的架构、数据库、接口、Agent、安全和实施文档。
3. 任务状态、`attempt_no`、幂等、Outbox、Kafka/Celery 恢复规则发生变化时，至少同步检查《总体架构与技术决策》《数据库与任务状态设计》《系统接口与服务契约》《开发实施与验收计划》。
4. RAG、Embedding、Agent Memory 的数据结构、检索边界或保留规则变化时，至少同步检查《Agent工作流与证据规范》《数据库与任务状态设计》《认证权限与安全设计》《系统接口与服务契约》。
5. 修订必须记录：原决策、变更原因、证据、影响文档、迁移/兼容影响、测试结果和必要的回滚方案。不得只改单份文档后默认其余文档仍然一致。
6. 本轮 V1.1 变更摘要：统一项目名称和支持范围；将 RAG/Embedding/Agent Memory 纳入当前设计；明确 BGE-M3 + PostgreSQL/pgvector 首选方向；补充外部模型数据确认、用户隔离、可观测性与基线/优化/复测要求。
