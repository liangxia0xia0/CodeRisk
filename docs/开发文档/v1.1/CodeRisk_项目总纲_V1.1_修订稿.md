## 一、项目定位

### 1.1 产品是什么

CodeRisk 是一个面向 Java、Python 代码变更的网页端风险评估与任务难度量化平台。

用户在网页端提交 Diff 文本或 Diff 文件。系统分析本次变更，生成结构化的评估计划书，帮助用户理解：

- **变更风险：** 哪些改动可能引入问题，风险等级如何，依据是什么。
- **影响分析：** 从本次 Diff 和可用证据出发，哪些行为、模块或边界值得重点关注；无法确认的影响必须标注为假设或待验证项。
- **任务难度（Hardness）：** 本次变更的复杂度、主要难点及判断依据。
- **测试计划：** 建议优先验证的场景、边界条件、回归范围与测试重点。
- **处理建议：** 推荐的审查重点、验证步骤和风险缓解措施。
- **证据与限制：** 结论关联的 Diff 位置、静态分析结果、检索材料或其他证据，并明确证据不足之处。

产品目标不是输出一段泛泛的代码解释，也不是让多个 Agent 自由聊天，而是把一次代码变更转化为有结构、有依据、可审阅的评估计划书。

### 1.2 核心用户与价值

首版面向独立使用平台的开发人员、代码审查人员和技术负责人。用户通过个人账号使用系统，不建设复杂的团队、组织或协作权限体系。

系统主要帮助用户在代码评审或合并前回答三个问题：

1. 这次改动可能带来什么风险？
2. 这次任务难在哪里，复杂度主要来自哪里？
3. 应该重点验证什么，才能更有把握地接受这次改动？

评估结果用于辅助判断，不代替开发者或审查人员作出最终决定。

### 1.3 首版业务闭环

1. 用户注册或登录。
2. 用户在网页端提交 Diff 文本或 Diff 文件，并在提交前明确确认：Diff 内容将发送给所配置的外部模型服务进行分析。
3. 后端创建分析任务并返回任务标识，前端展示排队、执行和结果状态。
4. 系统解析 Diff，提取能够可靠获得的变更事实，并通过分析工作流生成风险、难度、影响、证据和测试建议。
5. 系统保存任务结果与结构化报告。
6. 用户查看报告，并围绕报告内容继续追问或质疑。
7. 用户可以在符合业务规则时手动重试失败任务，或发起重新分析。重新分析创建新任务并保留旧报告，不覆盖历史结果。

### 1.4 首版明确不做的事

首版不包含：

- 自动修改用户代码、生成并应用补丁、自动提交或推送代码。
- 本地 Agent、读取用户本地仓库、自动克隆仓库。
- Git 仓库、Commit、Pull Request 的直接集成。
- 执行用户提交的代码、构建脚本或测试脚本。
- 以仅有的 Diff 为依据，声称已准确分析整个仓库的调用链、依赖图或完整影响范围。
- 复杂团队协作、组织管理和企业级多租户治理。
- 为展示技术而堆叠没有明确业务职责的组件。

如后续需要增加上述能力，必须作为新的范围变更评审，不得默认混入 MVP。

## 二、设计原则

### 2.1 真实业务，最小可落地

按照真实业务场景设计，但实现范围保持克制。最小实现不等于忽略认证、隔离、幂等、错误处理、数据保护和可观测性等基本工程要求。

### 2.2 先明确业务，再决定实现

产品需求回答“系统必须做什么”；总体架构回答“服务如何协作”；数据库文档回答“业务事实如何保存”；接口契约回答“组件如何通信”；实施计划回答“按什么顺序完成并验证”。

下游文档不得擅自改变上游已确认的产品范围。

### 2.3 结论必须区分事实、推断和未知

能够通过确定性程序提取的事实，优先通过 Diff 解析、代码结构解析或静态分析获取。模型可以综合分析和解释，但报告必须区分：

- **已观察事实：** 能够从本次 Diff 或工具输出直接核验。
- **分析推断：** 根据已有证据推导出的可能风险或影响。
- **待验证假设：** 目前缺少足够信息，需要开发者进一步确认的事项。

不能把模型推断包装成已经验证的事实。

### 2.4 用户数据隔离是后端责任

多个用户共用一套部署，但每个用户只能访问自己拥有的任务、报告、对话及关联数据。前端隐藏入口不能代替后端授权检查。

### 2.5 提前考虑工程可靠性，分阶段验收

架构设计必须提前考虑异步任务、重复消息、幂等、失败恢复、超时、日志、指标和数据保留。实现可以分阶段推进，但不能在文档中留下互相矛盾的职责定义。

### 2.6 保护提交内容

Diff 可能包含源代码、内部路径、凭据或其他敏感信息。系统应明确外部模型调用的数据流与用户确认机制；日志不得记录原始 Diff、密码、访问令牌或模型密钥。输入大小、解析耗时和工具资源消耗必须受限。

## 三、已确认的技术方向

本节只记录当前已经确认的方向。具体依赖版本、表结构、接口路径、超时参数和部署配置由专项文档定义。

| 层次 | 当前方向 | 职责边界 |
|---|---|---|
| 前端 | React、TypeScript、Vite、Ant Design、TanStack Query | 登录、Diff 提交、任务状态、报告查看与追问 |
| 业务后端 | Go、Gin、GORM、PostgreSQL | 身份认证、权限、业务规则、任务生命周期、报告与审计数据 |
| Agent 服务 | Python、FastAPI、LangGraph | 分析流程编排、分析工具调用、结构化结果生成 |
| 跨服务事件 | Kafka | Go 与 Python 分析执行侧之间的可靠异步事件传递 |
| Python 内部任务 | Celery、Redis | Python 分析侧的任务调度与执行；不作为业务状态权威 |
| 检索与记忆 | RAG、Embedding、向量数据库、Agent Memory | 提供可检索的相关知识与受控的历史经验；具体数据范围、写入规则和存储方案由 Agent 专项设计明确 |
| 模型接入 | 统一模型适配层；首期 DeepSeek API | 隔离业务流程与模型供应商，便于后续评估 Ollama 等替代方案 |
| 部署 | Docker、Docker Compose、Nginx | 容器化运行、反向代理、配置管理与服务健康检查 |
| 代码事实提取 | Diff 解析、适用的 AST/静态分析工具 | 提供可核验的变更事实；不声称实现未覆盖的全仓分析 |

### 3.1 关键架构约束

1. **Go 是业务事实来源。** PostgreSQL 中的用户、任务、业务执行次数、任务状态和正式报告由 Go 业务侧维护。Python Agent 不直接写业务数据库。
2. **Kafka 与 Celery 职责不同。** Kafka 用于跨服务事件传递；Celery/Redis 用于 Python 分析侧内部调度。二者不能各自维护一套权威业务状态。
3. **可靠性规则必须一致。** 幂等键、Outbox、重复消费、任务尝试编号、超时收口、回调鉴权与迟到回调处理，需要在数据库设计和接口契约中形成同一套规则。
4. **RAG、向量检索与 Agent Memory 纳入设计范围。** 不能在没有明确决策记录的情况下，将它们默默改成“可选能力”。Agent 专项设计需要说明每项能力解决什么问题、存储什么数据、何时读取与写入、如何评测和删除。
5. **不默认引入 MCP。** 若没有明确的工具接入需求和收益，不为技术展示而增加 MCP。
6. **不建设代码执行沙箱。** MVP 不执行用户代码或测试脚本，因此不将 Sandbox 作为首版业务服务。
7. **模型凭据与用户数据分离。** 模型密钥只在服务端配置和使用，不要求用户部署模型；外部模型数据流必须在产品交互中明确说明。

## 四、服务部署的总体约束

总体架构与部署文档应至少明确以下部署单元及其通信关系：

- **Nginx / Web 前端：** 提供网页访问入口，并将 API 请求转发至 Go 业务后端。
- **Go 业务后端：** 对外提供 API，执行认证、授权、业务校验和数据库事务。
- **PostgreSQL：** 保存业务数据，是任务和报告的持久化权威。
- **Outbox 发布机制：** 将已提交的业务事务对应的事件可靠发布到 Kafka；可以先作为 Go 服务中的独立模块实现，不强制单独部署进程。
- **Kafka：** 传递跨服务分析任务事件。
- **Python Agent API / Worker：** 负责消费任务、执行 LangGraph 分析，并通过鉴权内部接口回传结构化结果。
- **Redis / Celery：** 支撑 Python 侧的内部调度与执行。
- **向量数据库：** 按 Agent 专项设计中已确定的检索需求部署，并通过独立的数据维护流程管理索引。

以上是部署职责，不意味着每个模块都必须拆成独立微服务。是否独立进程，应以故障隔离、扩展需求和实现成本为依据。MVP 使用 Docker Compose 管理运行环境；CI/CD、健康检查、迁移执行、持久化卷、密钥配置和备份验证应在工程实施计划中明确。

## 五、认证、安全与隐私基线

1. 支持邮箱注册与登录，不支持手机号注册登录。
2. 认证必须同时设计 Access Token 与 Refresh Token；具体传递方式、有效期、刷新轮换、撤销、登出及多端会话策略由《认证权限与安全设计》统一规定。本总纲不再预先限定为“只有 Access Token”。
3. 所有用户拥有的业务资源都必须进行后端所有权校验。
4. 提交 Diff 前，用户必须确认内容会发送给配置的外部模型服务。
5. 原始 Diff、密码、访问令牌和模型密钥不得进入普通应用日志。
6. 必须限制上传大小、文件类型、解析时间和资源消耗；拒绝不支持或格式异常的输入，并向用户返回可理解的错误。
7. 需要明确 Diff、报告、对话、记忆数据与审计记录的保留和删除规则；具体期限由安全设计和数据库设计统一定义。
8. Agent Memory 不得自动将所有用户 Diff、完整对话或历史报告沉淀为共享知识。其数据来源、用户隔离、人工确认条件和删除机制必须在 Agent 专项设计中明确。

## 六、测试与量化要求

测试分为两个阶段，不能只在开发结束时做一次演示。

### 6.1 第一轮：MVP 基线测试

核心闭环完成后，建立可复现的测试基线，至少覆盖：

- 业务流程、API 正确性和错误处理。
- 注册登录、双 Token 生命周期、权限校验与用户数据隔离。
- 任务状态流转、幂等、重复事件、重复/迟到回调、超时与恢复。
- Agent 输出结构正确性、证据有效性、风险判断、Hardness 评估和测试建议质量。
- RAG 检索质量、记忆读取与写入边界、历史数据隔离。
- PostgreSQL、Kafka、Redis/Celery 的故障与恢复行为。
- 并发请求、吞吐量、P95 延迟、错误率、CPU 与内存使用情况。
- 日志、关键指标、任务链路关联与敏感数据检查。

### 6.2 第二轮：优化后复测

根据第一轮真实测试结果，选择有证据支持的优化措施。尽量使用相同测试集、环境和负载条件复测，比较质量、延迟、吞吐量、错误率和资源使用，并检查是否引入副作用。

### 6.3 指标真实性

设计目标、预期指标和实测结果必须分开记录。未实际运行的测试不能标记为通过；未经验证的准确率、并发能力和性能提升比例不得写成项目成果或简历数据。

## 八、决策状态与变更治理

每项重要设计必须标明状态：

- **已确认：** 项目方向已达成一致。
- **待细化：** 方向已确认，具体规则需在专项文档中定义。
- **待验证：** 方案已确定为当前实施基线，但需通过实现或测试验证。
- **待讨论：** 尚未形成决定，不得当成已冻结要求。
- **已替代：** 已被后续明确决策取代。

新增或修改关键决策时，应记录：

1. 要解决的问题。
2. 当前决定及其理由。
3. 考虑过的替代方案。
4. 对产品、架构、数据库、接口、测试和实施计划的影响。
5. 需要同步修改的文档。
6. 需要通过什么证据验收。

需求追溯链应尽量完整：

**业务需求 → 架构决策 → 数据模型 → API/事件契约 → 实施任务 → 测试用例 → 测试结果。**

## 九、协作分工

- **ChatGPT：** 负责需求梳理、方案设计、文档编写、决策记录和跨文档一致性审查。
- **项目发起人：** 确认关键业务取舍，并审阅每阶段交付物。
- **Cursor：** 在设计基线确认后检查真实仓库、按小任务实施代码、运行测试并提供实际证据。

Cursor 不应在没有说明的情况下更改产品范围、业务规则或服务职责。如果实现遇到设计冲突、依赖限制或工程障碍，应先报告问题和影响，再决定是否修改文档。

每个实施任务必须写明目标、允许修改的范围、明确的非目标、验证命令和完成标准。未验收的任务不得作为已完成阶段的前置条件。
