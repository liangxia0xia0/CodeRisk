# CodeRisk 最终交叉审查报告

**文档版本：** V1.1（交叉审查稿）  
**审查状态：** 有条件通过；发现需在正式实施前修正的文档冲突  
**审查范围：** 本轮 V1.1 修订稿，包括项目总纲、PRD、总体架构、Agent 工作流与证据规范、数据库与任务状态设计、系统接口与服务契约、认证权限与安全设计、开发实施与验收计划、设计决策与变更记录、README。  
**重要限制：** 本报告检查的是设计文档，不代表代码已实现、部署已成功或测试已通过。

## 一、结论摘要

当前文档包已经形成较清晰的产品与工程基线：Web 端提交 Diff；Go + PostgreSQL 管理业务事实；Python Agent 负责分析并通过受鉴权的内部契约回传；Kafka/Outbox 负责跨服务事件；Celery/Redis 负责 Python 内部任务调度；分析结果强调证据追溯和推断边界；开发验收采用基线测试、优化、同条件复测的顺序。

**但现在不应把文档包标记为“全部一致、最终冻结”。** 本次审查发现至少两处明确冲突，以及几项实施前必须核实的契约细节。建议先修复 P0 文档冲突，再把剩余项目转成实现任务和测试门禁。

## 三、必须修正的文档冲突

### P0-1：PRD 的功能清单与“不支持取消”章节冲突

**证据：** PRD 第 3 章功能清单仍出现“用户取消已提交任务”；第 4.6 节明确写“不支持取消”，并说明没有取消接口或状态。架构、数据库、接口与决策记录也均采用“不支持取消”的方向。

**判定：** 这是明确的同文档冲突，可能误导前端、API 和状态机实现。

**修正要求：** 从 PRD 的功能清单中删除“用户取消已提交任务”；检查验收标准、用户故事和接口目录中是否还有将取消描述为 MVP 功能的内容。统一保留“不支持取消”。

### P0-2：向量存储选型在架构文档内部及跨文档之间不一致

**证据：** V1.1 架构文档多处将 BGE-M3 + PostgreSQL/pgvector 写为当前优先方向，但第 4 章相关段落仍称“向量存储技术仍需定案”，并要求专项设计前不得暗示选定；后续技术决策表又把 pgvector 写为优先评估、选型待定。与此同时，Agent、数据库、接口、实施计划和决策记录的 V1.1 修订稿已按 BGE-M3 + pgvector 作为首选方案展开。

**判定：** 当前无法仅凭架构文档判断 pgvector 是已选定的 MVP 设计基线，还是尚未决策的候选项。

**修正要求：** 项目方需在两种表述中统一一种。建议采用：**“MVP 默认方案为 PostgreSQL + pgvector；BGE-M3 为首选 Embedding 模型。该组合是设计基线，仍需通过目标环境兼容性、检索质量、延迟、资源占用和用户过滤测试验证；若验证不通过，再以明确证据重新评估。”** 随后同步架构正文、技术决策表、决策记录、实施计划和 README。不要把“首选设计”表述成“效果已验证”。

## 四、实施前必须补齐或核实的事项

以下项目不一定是业务决策冲突，但当前文档还不足以证明已经形成可直接实现、可自动验收的完整契约。

### P1-1：认证与令牌生命周期必须形成唯一契约

V1.1 已明确使用 Access Token + Refresh Token，但实现前仍需核实并统一：Refresh Token 是 Cookie 还是请求体传递；Cookie 场景下 CSRF 防护如何执行；刷新是否轮换令牌；旧令牌重用如何检测；登出与撤销如何落地；多设备会话是否支持。安全文档、API 契约和数据库模型应对齐，不应只停留在原则描述。

### P1-2：RAG 与 Agent Memory 的物理结构、权限和生命周期需要落到可测试规则

需要在实现前明确并测试：知识源如何创建、更新、失效与删除；文档切分和 Embedding 版本如何关联；向量维度变化如何迁移；检索结果如何过滤用户/知识域；Memory 由哪些事件生成、哪些状态可检索、用户如何删除或纠正；报告如何记录知识与记忆引用。所有跨用户查询必须有负向隔离测试。

### P1-3：任务状态、Outbox、Kafka 去重与 Celery 恢复要以状态转换表和故障测试收口

数据库、架构和接口已描述大部分原则。实施前应确保同一份状态转换表能明确：允许的源状态/目标状态、触发者、事务边界、重复事件行为、迟到回调行为、超时收口条件、重试是否递增 `attempt_no`。至少覆盖重复 HTTP 请求、同幂等键不同内容、重复 Kafka 事件、Celery 接收后进程崩溃、重复/迟到回调、Outbox 重发和恢复窗口内任务。

### P1-4：默认超时需要按层定义，避免参数含义重叠

当前常见基线为模型单次调用 30 秒、发布/排队等待 120 秒、任务执行 180 秒、恢复判定窗口 60 秒，基础设施重投最多 3 次并采用约 1/2/4 秒退避。实现时必须明确各时钟的起点、截止时间、是否包含排队时间，以及模型重试和结构修正是否计入总执行预算。数值应先作为可配置基线，不应声称是已测得的最佳参数。

### P1-5：Diff 解析能力必须与输入边界一致

系统只接收 Diff，不能据此声称已经确认全仓调用链、真实运行时影响或未提供文件的行为。架构文档提到 AST、依赖与静态分析时，应注明每项能力的实际输入前提、支持语言与失败降级策略；不具备上下文时报告应明确标记为推断或待验证假设。

### P1-6：外部模型确认的覆盖范围与记录粒度

文档约定同一线程后续追问和重新分析沿用已留存确认。实现前应明确确认记录关联用户、线程、任务、模型供应商及隐私告知版本的方式，并评估当供应商、用途或告知内容变化时是否需要重新确认。确认记录应可审计，但不能存储原始 Diff 或密钥作为证明材料。

## 五、文档状态与事实边界

1. V1.1 文档是设计修订稿，不能据此声称服务、数据库迁移、Kafka、Celery、RAG 或 Memory 已实现。
2. BGE-M3、pgvector、超时参数和重试参数目前是设计选择/基线，效果与兼容性仍需测试。
3. 评测指标必须来自固定数据集和可复现运行记录；不得预填成功率、P95、吞吐量或成本结果。
4. 每个实施阶段都应保留命令、环境、配置、测试输出和未通过项；未执行测试标记为“未运行”，而非“通过”。

## 六、建议的修正顺序

1. 先修正 P0-1：清除 PRD 功能清单中与“不支持取消”冲突的条目。
2. 再修正 P0-2：明确 pgvector 是默认设计基线还是待定选型，并同步所有文档。
3. 将 P1-1 至 P1-6 拆为实现前检查项，分别落实到认证契约、RAG/Memory 设计、任务状态与事件契约、配置说明和测试计划。
4. 重新运行文档关键词与交叉引用检查，确认旧版本术语没有混入当前 README 和修订稿。
5. 进入编码前，先检查实际仓库和运行环境；按开发实施计划逐阶段开发，不要一次性生成整套代码。

## 七、最终审查结论

**结论：有条件通过，暂不建议标记为“最终冻结”。** 产品输入范围、业务数据归属、异步架构、手动重试边界、模型数据外发确认、证据追溯和测试原则已基本统一；但 PRD 取消功能残留与向量存储选型表述冲突必须先修正。其余 P1 项目应在对应模块编码前完成契约化，并通过自动化测试验证。

本报告本身也属于 V1.1 审查稿。完成上述修正后，应更新本报告结论，并以实际仓库、迁移脚本、API schema、事件 schema 和测试记录作为实施验收依据。
